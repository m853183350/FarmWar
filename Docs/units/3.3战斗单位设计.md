# 战斗单位设计

本文档设计战斗单位的数据运算分层、基类架构、以及与现有非战斗单位（FarmWorker）的差异。

---

## 一、核心问题：Tick vs Physics 帧的分层策略

### 1.1 现有架构回顾

当前项目中，非战斗单位（FarmWorker → UnitBase）完全由 **Tick 系统（20Hz）** 驱动：

```
TickSystem.tick_elapsed (20Hz)
  → UnitBase._on_tick(delta)
    → 逻辑移动（grid_position 直接步进）
    → AI 决策（任务队列）
    → 工作进度

_process(delta) (60+ FPS)
  → 画面插值（grid_position → global_position.move_toward）
```

这套方案适合 FarmWorker 的原因：
- FarmWorker 不与敌方单位发生物理碰撞
- FarmWorker 移动目标已知（任务指定的地块），路径由 A* 预计算
- 不需要实时碰撞检测或物理交互
- 20Hz 的频率足以驱动工作进度、移动步进等逻辑

但战斗单位有**根本不同的需求**：

| 需求 | FarmWorker（非战斗） | 战斗单位 |
|------|---------------------|----------|
| 碰撞检测 | 不需要 | **必须** — 单位间有碰撞体，存在推挤/分离 |
| 击退/位移效果 | 不需要 | **必须** — 技能可造成强制位移 |
| 实时命中判定 | 不需要 | **必须** — 攻击动画帧级精度的 hitbox 判定 |
| 弹射物飞行 | 不需要 | **必须** — 弹射物需要逐帧位置更新 |
| 移动精度要求 | 低（网格级） | 高（需要平滑物理移动） |
| 目标精确性要求 | 中等（到相邻格即可） | 高（需精确接触攻击目标） |

### 1.2 核心结论

**战斗单位采用"Tick 管逻辑，Physics 管物理"的双层架构：**

```
┌─────────────────────────────────────────────────────┐
│                   Tick 层 (20Hz)                      │
│  • AI 决策（状态机：巡逻→追击→攻击→逃跑）               │
│  • 目标选择（最近敌人 / 最低血量 / 最高威胁）           │
│  • 攻击/技能冷却计时                                    │
│  • 伤害公式计算                                        │
│  • Buff/Debuff 计时与叠层                               │
│  • 生命/法力恢复                                        │
│  • 战略移动指令（设置 move_target）                     │
│  • 状态转换（IDLE→CHASE→ATTACK→COMBAT→DEAD）          │
├─────────────────────────────────────────────────────┤
│                Physics 帧 (60Hz)                      │
│  • 移动执行（velocity + acceleration + move_and_slide）│
│  • 碰撞检测与响应（单位间推挤、墙碰撞）                   │
│  • 击退/冲锋/强制位移（力道施加）                        │
│  • Hitbox/Hurtbox Area2D 重叠检测                       │
│  • 弹射物飞行（速度 + 碰撞）                             │
│  • 死亡 ragdoll / 物理抛出                              │
└─────────────────────────────────────────────────────┘
```

### 1.3 数据归属详细对照表

| 数据/行为 | Tick (20Hz) | Physics (60Hz) | 理由 |
|-----------|:-----------:|:--------------:|------|
| **AI 目标选择** | ✅ | | 战略决策，一个 tick 的延迟无影响 |
| **AI 状态转换** | ✅ | | 状态机切换不依赖帧率 |
| **移动方向/速度设定** | ✅ | | Tick 设定 `target_velocity`，Physics 执行 |
| **移动执行（碰撞）** | | ✅ | 需要帧级碰撞检测 |
| **攻击冷却 (cooldown)** | ✅ | | 计时器，tick 精度足够 |
| **攻击动画触发** | ✅ | | 战略决策"开始攻击"在 tick |
| **Hitbox 生命周期** | ✅ | | Tick 决定"第 N tick 激活 hitbox" |
| **Hitbox 重叠检测** | | ✅ | Area2D 的 `area_entered` 是物理帧信号 |
| **伤害计算** | ✅ | | 数学公式，确定性计算 |
| **击退生效** | ✅ | | Tick 决定"施加击退"，Physics 执行力度 |
| **击退位移执行** | | ✅ | 作为 velocity/impulse 在物理帧执行 |
| **Buff 计时/叠层** | ✅ | | 固定间隔倒数，帧率无关 |
| **HP/MP 恢复** | ✅ | | 周期性恢复，帧率无关 |
| **弹射物发射** | ✅ | | Tick 决定"生成弹射物" |
| **弹射物飞行** | | ✅ | 需要碰撞检测才命中目标 |
| **路径规划（A*）** | ✅ | | 已有异步寻路系统 |
| **对路径的物理追踪** | | ✅ | combat 单位以 velocity 沿路径移动 |
| **死亡判定** | ✅ | | HP ≤ 0 的判定在 tick |
| **死亡动画/物理** | ✅ / | ✅ | 动画在 tick 触发，物理（如 ragdoll）在物理帧 |

### 1.4 两层之间的通信协议

```
Tick 层 → Physics 层（单向数据流）:
  - target_velocity: Vector2      # AI 设定的期望速度
  - pending_knockback: Vector2    # 待施加的击退冲量
  - active_skill_phase: int       # 当前技能执行阶段（-1=无, 0=前摇, 1=判定帧, 2=后摇）
  - hitbox_active: bool           # 是否激活 hitbox Area2D

Physics 层 → Tick 层（通过信号回传）:
  - collision_occurred(unit)      # 与其他单位碰撞
  - hitbox_hit(target_unit)       # hitbox 检测到 hurtbox（需去重）
  - stuck_detected()              # 卡住（无法移动）
  - move_blocked()                # 路径阻塞
```

采用**单向数据流**：Tick 写入指令，Physics 执行并回传事件。避免双向依赖导致的状态不一致。

## 二、CombatUnitBase 类设计

### 2.1 继承关系

```
CharacterBody2D (Godot 内置)
  └── UnitBase (scripts/units/unit_base.gd)
        ├── FarmWorker (非战斗 — 纯 Tick 驱动)
        └── CombatUnitBase (战斗基类 — Tick+Physics 双层)
```

**没有 MeleeUnit / RangedUnit / EnemyBase 子类。** 所有战斗单位都是 `CombatUnitBase` 实例，差异通过**组件组合**和**配置数据**区分，而非继承。

**为什么不用继承区分兵种类型：**

| 如果用继承 | 问题 |
|-----------|------|
| `CombatUnitBase → MeleeUnit` | 远程和近战只是攻击技能的距离参数不同，不需要两个类 |
| `CombatUnitBase → EnemyBase` | 敌方只是 faction ≥ 1 + 挂载了 AI 控制器，与数据字段无关 |
| `EnemyBase → EnemyMelee` | 组合爆炸：Enemy × Melee、Enemy × Ranged、Ally × Melee… |

**组合方案：**

```
CombatUnitBase 实例
├── faction: int                          # 0=玩家, 1+=敌方（UnitBase 已有字段）
├── stats: CombatStats (Resource)         # 从 JSON 加载的属性模板
├── skills: Array[Skill]                  # 拥有的技能列表（含普攻）
├── ai_controller: AIController           # AI 控制器（所有战斗单位都挂载）
├── current_task: CombatTask?             # 当前任务（null = 自主模式）
└── （任务来源：CommandSystem 分派 或 自主 AI 无任务）
```

- **近战/远程** = `Skill` 的 `range` 和 `projectile_id` 字段决定
- **友方/敌方** = `faction` 字段 + 是否挂载 `AIController` 组件
- **不同兵种** = 不同的 `CombatStats` JSON 配置 + 不同的 `Skill` 列表

**设计原则：**
- `UnitBase` 保持不变，继续为 FarmWorker 提供纯 Tick 驱动的移动系统
- `CombatUnitBase` **覆写移动系统**，改为 Physics 驱动
- `CombatUnitBase` 不硬编码近战/远程/敌我逻辑——全部由组件和配置决定
- FarmWorker **不继承** CombatUnitBase，两者并列继承 UnitBase

| 属性 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `armor` | `float` | `0.0` | 护甲值（减免物理伤害） |

| `crit_chance` | `float` | `0.05` | 暴击率（0.0 ~ 1.0） |

#### CombatUnitBase 新增 — 移动系统覆写

| 属性 | 类型 | 说明 |
|------|------|------|
| `target_velocity` | `Vector2` | Tick 层设定的期望速度（AI 写入） |
| `current_velocity` | `Vector2` | Physics 层实际速度（move_and_slide 使用） |
| `acceleration` | `float` | 移动加速度（格/秒²），默认 20.0 |
| `deceleration` | `float` | 移动减速度，默认 20.0 |
| `knockback_resistance` | `float` | 击退抗性（0.0 ~ 1.0，1.0 = 免疫） |
| `pending_knockback` | `Vector2` | 待执行的击退向量（Tick 写入，Physics 消费） |

#### CombatUnitBase 新增 — 技能系统（普攻和技能统一管理）

**为什么把普攻也设计为技能：**

| 方面 | 普攻硬编码在 CombatUnitBase | 普攻作为 Skill |
|------|---------------------------|---------------|
| 近战/远程区分 | 需要 MeleeUnit、RangedUnit 子类 | `Skill.range` 字段即可区分 |
| 多段攻击 | 需要额外的连击系统 | 多段攻击是多个 Skill，AI 按优先级顺次释放 |
| 攻击动画阶段 | `attack_windup_ticks` 等硬编码 | `Skill.windup_ticks` / `active_ticks` / `recovery_ticks` |
| AoE 攻击 | 需要单独的 AoE 系统 | `Skill.hitbox_shape` 描述判定区形状 |
| 弹射物 | 需要 `projectile_spawned_this_attack` 标记 | `Skill.projectile_id` 决定是否发射弹射物 |
| 统一冷却 | 攻击冷却和技能冷却两套冷却系统 | 同一套冷却系统 |

| 属性 | 类型 | 说明 |
|------|------|------|
| `skills` | `Array[Skill]` | 拥有的技能列表（至少含 1 个 `is_basic_attack = true` 的普攻技能） |
| `skill_cooldowns` | `Dictionary` | 每个技能的剩余冷却 tick 数 `{skill_id: int}` |
| `active_skill` | `Skill` | 当前正在执行的技能（null = 无） |
| `active_skill_phase` | `int` | 当前技能的执行阶段：-1=无, 0=前摇, 1=判定帧, 2=后摇 |
| `skill_phase_remaining_ticks` | `int` | 当前阶段剩余 tick 数 |
| `hit_targets_this_cast` | `Array[CombatUnitBase]` | 本次技能施放已命中的目标（防重复命中） |
| `projectile_spawned_this_cast` | `bool` | 本次技能施放是否已发射弹射物 |

#### CombatUnitBase 新增 — Buff 系统

| 属性 | 类型 | 说明 |
|------|------|------|
| `active_buffs` | `Array[BuffData]` | 当前生效的 Buff 列表 |

> **BuffData 数据结构** 详见 [scripts/units/buff_data.gd](../../scripts/units/buff_data.gd)。
>
> Buff 的属性修改分为两层：
> - **加算层**（`stat_modifiers`）：直接加减数值，如 +10 攻击，-0.5 移速
> - **倍率层**（`stat_multipliers`）：加成比例，如 0.30 = +30%，-0.15 = -15%
>
> **多个 Buff 的倍率加成先求和再乘算：** `final_multiplier = 1.0 + Σ(bonus_i)`。
> 例如 Buff A +30%（0.30）、Buff B +20%（0.20）、Debuff C -15%（-0.15）：
> 总倍率 = 1.0 + 0.30 + 0.20 + (-0.15) = 1.35。
>
> 完整计算顺序见 [2.4.6 统一属性计算管道](#246-统一属性计算管道)。

#### CombatUnitBase 新增 — 控制器组件（组合模式）

| 属性 | 类型 | 说明 |
|------|------|------|
| `ai_controller` | `AIController?` | AI 控制器组件节点。**所有战斗单位都挂载**（敌方和友方都是 AI 驱动） |
| `current_task` | `CombatTask?` | 当前正在执行的任务（null = 无任务，进入自主 AI 模式） |

> **设计要点：** 玩家不逐单位操控，而是发高层指令。指令系统自动选中单位、创建任务、分派。单位只知道自己有没有任务——有任务就优先执行任务，没任务就走自主 AI（巡逻/警戒/自动索敌）。所有单位的决策都由 `AIController` 统一管理，只是任务来源不同（指令系统 vs 自主扫描）。

### 2.3 战斗状态机扩展

在 `UnitState` 基础上，战斗单位的状态转换逻辑扩展：

```
                    ┌──────────────────────────────────┐
                    │                                  │
                    ▼                                  │
    ┌──────┐  发现敌人  ┌────────┐  进入射程  ┌───────┐│
    │ IDLE │ ────────→ │ CHASE  │ ────────→ │CASTING││ ← 施放技能（含普攻）
    └──────┘            └────────┘            └───────┘│
       ↑                    │                    │     │
       │         丢失目标    │    目标脱离射程    │     │
       │                    ▼                    │     │
       │              ┌──────────┐               │     │
       │              │  RETURN  │←──────────────┘     │
       │              └──────────┘     技能完成/目标死亡 │
       │                    │                          │
       │         回到出生点  │                          │
       │                    ▼                          │
       │              ┌──────────┐                     │
       └──────────────│   IDLE   │←────────────────────┘
                      └──────────┘
    
    所有状态 → DEAD (HP ≤ 0)
```

| 状态 | 行为 | Tick 层职责 | Physics 层职责 |
|------|------|------------|---------------|
| `IDLE` | 站立不动，周期性扫描敌人 | 扫描范围、目标选择 | 维持 velocity = 0 |
| `CHASE` | 向目标移动，进入技能射程 | 设定移动目标、路径规划 | 执行 move_and_slide |
| `CASTING` | 施放技能（普攻也是技能） | 技能阶段推进、冷却计时、伤害结算 | hitbox/hurtbox 检测 |
| `RETURN` | 返回出生点/守卫位置 | 设定返回路径 | 执行移动 |
| `FLEE` | 低血量逃跑 | AI 判断逃跑方向 | 执行移动 |
| `STUNNED` | 被控制，无法行动 | 控制计时 | 维持 velocity = 0（可被击退覆盖） |

> **注意：** 战斗单位的状态机替代了 FarmWorker 的任务队列系统。FarmWorker 用 `MOVING + WORKING` 完成任务，CombatUnitBase 用 `CHASE + CASTING` 进行战斗。没有独立的 `ATTACK` 状态——攻击只是释放一个技能（`is_basic_attack = true`），走 `CASTING` 状态。

### 2.4 技能执行系统（替代原"攻击系统"）

普攻和特殊技能统一走同一套执行流程。CombatUnitBase 只负责**执行技能**，不区分"这是普攻还是技能"。

#### 2.4.1 Skill 数据结构

```gdscript
class_name Skill
extends Resource

## 技能唯一 ID（如 "basic_slash", "fireball"）
@export var skill_id: StringName

## 技能显示名称
@export var display_name: String

## 是否为普攻（true = 普攻，AI 会优先使用；false = 特殊技能）
@export var is_basic_attack: bool = false

## 伤害类型
@export var damage_type: DamageType  # PHYSICAL / MAGIC / TRUE

## 基础伤害值（可为 0，伤害来自单位自身的 buff 加成）
@export var base_damage: float = 0.0

## 伤害倍率（最终伤害 = (unit_attack_power + base_damage) × damage_multiplier）
@export var damage_multiplier: float = 1.0

## 技能射程（格数，≤1.5 = 近战，>1.5 = 远程）
@export var range: float = 1.5

## 冷却时间（tick 数，20 tick = 1 秒）
@export var cooldown_ticks: int = 20

## 法力消耗
@export var mana_cost: float = 0.0

## 前摇 tick 数（施放动作，可被打断）
@export var windup_ticks: int = 5

## 判定帧持续 tick 数（hitbox 激活期间）
@export var active_ticks: int = 3

## 后摇 tick 数（收招动作）
@export var recovery_ticks: int = 8

## 弹射物 ID（null = 近战/无弹射物，非 null = 远程，从 projectile_db 获取模板）
@export var projectile_id: StringName

## 弹射物速度（格/秒，仅远程有效）
@export var projectile_speed: float = 10.0

## Hitbox 形状类型
@export var hitbox_shape: HitboxShape  # POINT / CIRCLE / ARC / RECT

## Hitbox 参数（半径、角度、宽高）
@export var hitbox_params: Dictionary = {}

## 技能动画名（AnimationPlayer 中的动画名）
@export var anim_windup: StringName
@export var anim_active: StringName
@export var anim_recovery: StringName

## AI 使用权重（越高越优先，0 = AI 不使用该技能）
@export var ai_priority: int = 1
```

#### 2.4.2 技能执行流程（普攻和技能共用）

```
Tick 层 — 每 tick:
  # 1. 如果当前有技能在执行，继续推进阶段
  if active_skill != null:
    _advance_skill_phase()
    return

  # 2. 更新所有技能冷却
  for skill_id in skill_cooldowns:
    skill_cooldowns[skill_id] -= 1

  # 3. 选择下一个技能（由控制器决定）
  var chosen: Skill = _controller.select_skill(skills, current_target)
  if chosen == null:
    return  # 无可用技能或无需施放

  # 4. 检查射程
  if distance_to(current_target) > chosen.range:
    _set_state(CHASE)  # 需要靠近
    return

  # 5. 开始施放
  _start_skill(chosen)

_start_skill(skill):
  active_skill = skill
  active_skill_phase = 0                           # 前摇
  skill_phase_remaining_ticks = skill.windup_ticks
  animation_controller.play_work(skill.anim_windup, skill.windup_ticks * tick_interval)
  hit_targets_this_cast.clear()
  projectile_spawned_this_cast = false

_advance_skill_phase():
  skill_phase_remaining_ticks -= 1
  if skill_phase_remaining_ticks > 0:
    return

  match active_skill_phase:
    0: # 前摇结束 → 进入判定帧
      active_skill_phase = 1
      skill_phase_remaining_ticks = active_skill.active_ticks
      hitbox_active = true  → Physics 层激活 hitbox Area2D
      animation_controller.play_work(active_skill.anim_active, ...)
      # 如果是远程技能，生成弹射物
      _try_spawn_projectile()

    1: # 判定帧结束 → 进入后摇
      active_skill_phase = 2
      skill_phase_remaining_ticks = active_skill.recovery_ticks
      hitbox_active = false  → Physics 层停用 hitbox
      animation_controller.play_work(active_skill.anim_recovery, ...)

    2: # 后摇结束 → 技能完成
      _finish_skill()

_finish_skill():
  skill_cooldowns[active_skill.skill_id] = active_skill.cooldown_ticks
  current_mana -= active_skill.mana_cost
  active_skill = null
  active_skill_phase = -1

Physics 层 — hitbox area_entered(hurtbox):
  if not hitbox_active: return
  if target in hit_targets_this_cast: return  # 已命中（单次技能每个目标只命中一次）
  → 发送 hitbox_hit(target) 信号
  → Tick 层计算伤害并应用
```

#### 2.4.3 近战 vs 远程的区分

**完全由 `Skill` 数据决定，不需要代码层面的分支：**

| Skill 字段 | 近战（如斩击） | 远程（如火球） |
|-----------|--------------|--------------|
| `range` | `1.5`（紧邻） | `8.0`（8格） |
| `projectile_id` | `""`（空） | `"fireball"` |
| `hitbox_shape` | `ARC`（扇形） | —（弹射物自带碰撞） |
| `anim_active` | `"slash"` | `"throw"` |

**同一个单位可以同时拥有近战和远程技能。** 例如一个单位有近战普攻 + 远程火球技能，AI 根据距离和目标选择使用哪一个。

#### 2.4.5 伤害计算（不变，但 damage 来源改为 Skill）

```
# 伤害 = Skill 的 base_damage + 单位攻击力（来自 Buff 加成）
raw_damage = (skill.base_damage + unit_attack_power_from_buffs) × skill.damage_multiplier
crit_or_not = randf() < unit.crit_chance ? crit_multiplier : 1.0
damage_dealt = raw_damage × crit_or_not

armor_factor = 100.0 / (100.0 + (skill.damage_type == MAGIC ? magic_resist : armor))
effective_damage = damage_dealt × armor_factor

if skill.damage_type == TRUE:
    effective_damage = damage_dealt  # 真实伤害无视抗性
```

#### 2.4.6 统一属性计算管道

战斗单位的属性（如 `attack_power`、`move_speed`、`armor`）可能来自多个系统：

- **玩家道具系统**（PropManager → ModifierRegistry → Domain）：全局被动修改
- **Buff 系统**（BuffData）：单位级战斗效果
- **装备/科技树等**（未来）

为保证无遗漏、顺序正确，所有属性查询必须通过单一入口 `get_effective_stat()`：

```
第 0 层：BASE = 单位 JSON 配置的原始值（如 attack_power = 10.0）

第 1 层：全局被动（ModifierRegistry，"unit" 域）
         ↓ result = PropManager.query_modifier("unit", stat_name, base, unit_context)
         ↓ 例：道具"将军令" flat +15 → result = 25.0

第 2 层：Buff 加算（所有 active_buffs 的 stat_modifiers 求和）
         ↓ for buff in active_buffs: result += buff.get_stat_modifier(stat_name)
         ↓ 例：Buff "战斗怒吼" +5 → result = 30.0

第 3 层：Buff 倍率加成求和（所有 active_buffs 的 stat_multipliers 求和后统一乘算）
         ↓ total_mult = 1.0 + Σ buff.get_stat_multiplier_bonus(stat_name)
         ↓ result *= total_mult
         ↓ 例：Buff A +30%, Buff B +20%, Debuff C -15%
         ↓     total_mult = 1.0 + 0.30 + 0.20 + (-0.15) = 1.35
         ↓     result = 30.0 × 1.35 = 40.5

输出：FINAL = 40.5
```

**关键规则：**
1. **全局被动先于局部 Buff**——道具代表战略基线，Buff 是在此基础上的战术调整
2. **加算先于乘算**——`(Base + ΣFlat) × (1.0 + ΣMultiplierBonus)`，确保百分比 Buff 对道具加成也生效
3. **多个倍率加成求和而非求积**——`1.0 + bonus_a + bonus_b` 而非 `(1.0 + bonus_a) × (1.0 + bonus_b)`。这样 +50% 和 +50% 得到 +100%（翻倍），而非 +125%（1.5×1.5），数值可控
4. **同层内按 priority 排序**——BuffData.priority 越小越先计算

```gdscript
## CombatUnitBase 中的统一属性查询方法（Phase 2 实现）。
func get_effective_stat(stat_name: String, base_value: float) -> float:
    var result: float = base_value

    # 第 1 层：玩家全局道具被动（ModifierRegistry → "unit" 域）
    if PropManager:
        result = PropManager.query_modifier("unit", stat_name, result, _build_stat_context())

    # 第 2 层：Buff 加算修改（按 priority 排序）
    var sorted_buffs: Array[BuffData] = active_buffs.duplicate()
    sorted_buffs.sort_custom(func(a, b): return a.priority < b.priority)
    for buff: BuffData in sorted_buffs:
        result += buff.get_stat_modifier(stat_name)

    # 第 3 层：Buff 倍率加成求和（按 priority 排序）
    var total_mult: float = 1.0
    for buff: BuffData in sorted_buffs:
        total_mult += buff.get_stat_multiplier_bonus(stat_name)
    result *= total_mult

    return result

## 构建传递给 ModifierRegistry 的单位上下文（用于 target_filter 匹配）。
func _build_stat_context() -> Dictionary:
    return {
        "unit_type": unit_type,
        "faction": faction,
        "unit_id": unit_id,
    }
```

**与 CombatSystem 的集成：**

```
伤害计算完整流程：
  attack_power = combat_unit.get_effective_stat("attack_power", base_attack_power)
  → CombatSystem.calculate_damage(skill, attack_power, crit_chance, crit_multiplier, armor, magic_resist)
    → 基础伤害 = (skill.base_damage + attack_power) × skill.damage_multiplier
    → 暴击判定
    → 抗性减免
```

> **设计意图：** `CombatSystem.calculate_damage()` 接收的 `attack_power` 已经是通过 `get_effective_stat()` 解析后的最终值。这样伤害计算本身保持纯函数，不感知属性来源。

### 2.5 AI 系统设计 — 控制器组件模式

AI 不写在 CombatUnitBase 中，而是作为**可插拔的组件节点**挂载在场景树上。这样做的好处：

- 玩家单位和敌方单位可以共用同一个 `CombatUnitBase` 类
- 切换阵营时只需替换控制器（测试时把敌方改为友方）
- AI 行为可以独立测试和迭代
- 未来可以给同一个单位类型挂不同的 AI（如"激进型"和"保守型"敌人）

#### 2.5.1 AIController 双模式架构

所有战斗单位（友方和敌方）都由 `AIController` 驱动。控制器有两种运行模式：

```
AIController 每 tick 决策:

  if unit.current_task != null:
    运行「任务优先模式」
      → 执行任务目标（移动到区域、守卫点位等）
      → 途中遭遇敌人 → 自动自卫（切换战斗行为）
      → 敌人清除 → 继续执行任务
      → 任务完成 → current_task = null → 回到自主模式
  else:
    运行「自主模式」
      → 默认行为：GuardBehavior（原地警戒）或 PatrolBehavior（区域游荡）
      → 扫描到敌人 → HatredSystem 更新仇恨
      → 有仇恨目标 → ChaseBehavior → CombatBehavior → 战斗
      → HP 过低 → FleeBehavior 逃跑
      → 战斗结束 → 回到默认行为
```

```
CombatUnitBase
└── AIController (Node)              ← 所有战斗单位都挂载
    ├── HatredSystem (Node)          #   仇恨系统
    ├── SkillSelector (Node)         #   技能选择器
    └── BehaviorFSM (Node)           #   行为状态机
        ├── ExecuteTaskBehavior      #   执行任务（优先于所有自主行为）
        ├── GuardBehavior            #   原地警戒（自主模式默认）
        ├── PatrolBehavior           #   区域游荡（自主模式可选）
        ├── ChaseBehavior            #   追击敌人
        ├── CombatBehavior           #   战斗（索敌→靠近→施放技能）
        └── FleeBehavior             #   低血量逃跑
```

#### 2.5.2 AIController 职责范围

| 职责 | 说明 | 实现位置 |
|------|------|---------|
| **模式判断** | 有 `current_task` → 任务模式；无任务 → 自主模式 | `AIController` |
| **任务执行** | 按 CombatTask 的类型执行对应行为（移动到区域、守卫等） | `ExecuteTaskBehavior` |
| **自卫中断** | 执行任务途中遇敌，自动切入战斗，战后恢复任务 | `BehaviorFSM` |
| **仇恨系统** | 确定攻击优先级：谁在打我 > 谁离得近 > 谁血量低 > 谁威胁高 | `HatredSystem` |
| **技能选择** | 从 `get_available_skills()` 中选最优技能 | `SkillSelector` |
| **自主行为** | 无任务时的默认行为：警戒（`GuardBehavior`）或游荡（`PatrolBehavior`） | `BehaviorFSM` |
| **战斗行为** | 发现敌人→追击→进入射程→施放技能→目标死亡→回到自主模式 | `ChaseBehavior` + `CombatBehavior` |
| **逃跑判断** | HP < 阈值 或 队友全灭 → 触发逃跑 | `FleeBehavior` |
| **寻路方式** | 通过 `PathfindingManager` 异步请求路径，设定 `target_velocity` | `ChaseBehavior` / `ExecuteTaskBehavior` |
| **警戒范围** | 扫描范围内敌方单位，更新仇恨列表 | `HatredSystem` |
| **全局指令响应** | 全体集合/全体撤退 → 通过 EventBus 信号覆盖当前行为 | `AIController` |

#### 2.5.3 仇恨系统

#### 2.5.4 技能选择器

```gdscript
class_name SkillSelector
extends Node

## 从可用技能中选择最优技能执行。
## 由 AIController 每 tick 调用（仅当无 active_skill 时）。
func select_skill(available: Array[Skill], target: CombatUnitBase, unit: CombatUnitBase) -> Skill:
    if available.is_empty():
        return null

    # 过滤条件
    var candidates: Array[Skill] = []
    for skill: Skill in available:
        # 检查是否在射程内
        if unit.grid_position.distance_to(target.grid_position) > skill.range * TILE_SIZE:
            continue
        # 普攻不耗蓝，优先候选
        candidates.append(skill)

    if candidates.is_empty():
        return null  # 无可用的技能（需要靠近目标）

    # 优先级排序：ai_priority 降序 → 普攻优先（当 DPS 足够时）
    candidates.sort_custom(func(a, b):
        if a.ai_priority != b.ai_priority:
            return a.ai_priority > b.ai_priority
        # 同优先级时，普攻优先（省蓝）
        if a.is_basic_attack and not b.is_basic_attack:
            return true
        return false
    )

    # 特殊逻辑：如果目标血量很低（可斩杀），优先用普攻节约法力
    if target.current_health < 20.0:
        for skill in candidates:
            if skill.is_basic_attack:
                return skill

    return candidates[0]
```

### 2.6 移动系统覆写

CombatUnitBase 覆写 UnitBase 的移动系统，从"Tick 逻辑步进"改为"Physics 驱动"：

```gdscript
# CombatUnitBase 覆写
func _on_tick(_delta: float) -> void:
    if state == UnitState.DEAD:
        return

    # Tick 层职责：由控制器组件决定行为
    _update_controller(_delta)        # 委托给 AIController（双模式：任务执行 / 自主行为）
    _update_buffs(_delta)             # Buff 计时
    _update_regen(_delta)             # 生命/法力恢复
    _update_skill_cooldowns(_delta)   # 技能冷却
    _update_skill_cast(_delta)        # 技能施放阶段推进

func _physics_process(_delta: float) -> void:
    if state == UnitState.DEAD:
        return

    # Physics 层职责：执行移动 + 碰撞
    # 加速度平滑移动
    var target_vel: Vector2 = target_velocity * move_speed * TILE_SIZE
    current_velocity = current_velocity.move_toward(target_vel, acceleration * TILE_SIZE * _delta)

    # 施加待处理的击退
    if pending_knockback.length() > 0.01:
        current_velocity += pending_knockback
        pending_knockback = Vector2.ZERO

    # 利用 Godot 物理引擎执行移动（含碰撞）
    velocity = current_velocity
    move_and_slide()

    # 同步 grid_position（供其他 Tick 系统读取）
    grid_position = global_position

    # 更新朝向
    if velocity.x != 0.0:
        facing_direction = Vector2(signf(velocity.x), 0.0)
```

**关键差异：**
- **UnitBase:** `_on_tick` 直接修改 `grid_position`，`_process` 插值画面
- **CombatUnitBase:** `_on_tick` 只设定 `target_velocity`，`_physics_process` 执行 `move_and_slide()`，自动处理碰撞

## 三、指令与任务系统

玩家不逐个操控作战单位，而是发出高层指令，系统自动完成"选兵 → 创建任务 → 分配 → 单位自主执行"的全流程。

### 3.1 玩家交互模型

```
玩家操作（框选区域 + 选择指令类型 + 兵力数量）
  → CommandSystem 接收指令
  → UnitSelection 自动选取符合条件的空闲作战单位
  → CombatTaskFactory 创建 CombatTask
  → UnitManager 分发 CombatTask 到选中的单位
  → 单位 AIController 检测到 current_task ≠ null → 进入任务模式
  → 单位自主执行任务（移动、索敌、战斗、返回）
```

### 3.2 指令类型

| 指令 | 说明 | 参数 | 任务行为 |
|------|------|------|---------|
| `EXPLORE` | 探索指定区域 | `center: Vector2, radius: float` | 移动到区域中心 → 在 radius 范围内巡逻游荡 → 自主索敌战斗 → 敌人清除后继续巡逻 |
| `GUARD` | 守卫指定位置 | `position: Vector2` | 移动到守卫点 → 原地警戒 → 敌人在警戒范围内自动攻击 → 击杀后回到守卫点 |
| `ATTACK` | 攻击指定目标/区域 | `target: Vector2 / unit_id` | 移动到目标位置 → 优先攻击指定目标 → 清除区域内所有敌人 → 回到集合点 |
| `RALLY` | 全体集合（全局覆盖） | `position: Vector2` | 覆盖所有单位的当前任务 → 全部移动到集结点 → 待命 |
| `RETREAT` | 全体撤退（全局覆盖） | `retreat_point: Vector2` | 覆盖所有单位的当前任务 → 全部移动到撤退点 → 途中只还击不追击 |
| `HOLD` | 原地待命（全局覆盖） | — | 停止当前任务 → 原地不动 → 仍会自卫但不主动索敌 |

### 3.3 CombatTask 数据结构

```gdscript
class_name CombatTask
extends RefCounted

## 任务唯一 ID
var task_id: int = 0

## 任务类型
var task_type: CombatTaskType

enum CombatTaskType {
    EXPLORE,     # 探索区域
    GUARD,       # 守卫点位
    ATTACK,      # 攻击目标
    RALLY,       # 集合（全局覆盖）
    RETREAT,     # 撤退（全局覆盖）
    HOLD,        # 待命（全局覆盖）
}

## 目标位置（世界坐标）
var target_position: Vector2

## 目标区域半径（EXPLORE 模式下的巡逻范围）
var patrol_radius: float = 5.0

## 指定攻击目标 ID（ATTACK 模式下可选，null 表示区域内所有敌人）
var attack_target_id: StringName

## 任务状态
var status: CombatTaskStatus

enum CombatTaskStatus {
    PENDING,       # 等待执行
    IN_PROGRESS,   # 执行中
    COMPLETED,     # 已完成
    FAILED,        # 失败（路径不通等）
    OVERRIDDEN,    # 被全局指令覆盖
}

## 任务优先级（全局覆盖指令 = 最高优先级）
var priority: int = 0

## 创建时的游戏 tick
var created_tick: int = 0

## 所属单位 ID
var assigned_unit_id: StringName
```

### 3.4 CommandSystem（指令系统）

```gdscript
class_name CommandSystem
extends Node
## 挂在 GameRoot 下，非 Autoload

## 发出指令信号供 EventBus 广播
signal command_issued(command_type: CombatTask.CombatTaskType, params: Dictionary)

## 玩家发出高层指令的入口。
## [param command_type] 指令类型
## [param position] 目标位置
## [param unit_count] 所需兵力数量（-1 = 所有可用）
## [param unit_type_filter] 单位类型过滤（"" = 所有战斗单位）
func issue_command(
    command_type: CombatTask.CombatTaskType,
    position: Vector2,
    unit_count: int = -1,
    unit_type_filter: StringName = &""
) -> int:
    # 1. 如果是全局覆盖指令（RALLY / RETREAT / HOLD）
    if command_type in [CombatTask.CombatTaskType.RALLY,
                        CombatTask.CombatTaskType.RETREAT,
                        CombatTask.CombatTaskType.HOLD]:
        return _issue_global_override(command_type, position)

    # 2. 调用 UnitSelection 自动选兵
    var selected: Array[CombatUnitBase] = UnitSelection.select_units(
        position, unit_count, unit_type_filter, faction = 0
    )

    # 3. 为每个选中单位创建 CombatTask
    var tasks: Array[CombatTask] = []
    for unit: CombatUnitBase in selected:
        var task: CombatTask = CombatTaskFactory.create(command_type, position, unit.unit_id)
        tasks.append(task)

    # 4. 分发任务
    _distribute_tasks(tasks, selected)
    command_issued.emit(command_type, {"position": position, "count": selected.size()})
    return selected.size()
```

### 3.5 UnitSelection（自动选兵）

```gdscript
class_name UnitSelection
extends RefCounted
## 纯工具类，静态方法

## 自动选取符合条件的空闲作战单位。
## [param from_position] 从哪个位置算距离（选最近的）
## [param count] 选取数量（-1 = 不限）
## [param unit_type_filter] 单位类型过滤（"" = 不限）
## [param faction] 阵营过滤
static func select_units(
    from_position: Vector2,
    count: int,
    unit_type_filter: StringName,
    faction: int
) -> Array[CombatUnitBase]:
    var candidates: Array[CombatUnitBase] = []

    # 从 UnitManager 获取所有活跃战斗单位
    for unit: CombatUnitBase in UnitManager.get_combat_units():
        # 过滤条件
        if unit.faction != faction:
            continue
        if not unit.is_alive():
            continue
        if unit_type_filter != &"" and unit.unit_type != unit_type_filter:
            continue
        # 只选空闲的（IDLE 状态，无当前任务）
        if unit.current_task != null:
            continue
        if unit.state != UnitBase.UnitState.IDLE:
            continue
        candidates.append(unit)

    # 按距离排序（最近的优先）
    candidates.sort_custom(func(a, b):
        return a.grid_position.distance_squared_to(from_position) <
               b.grid_position.distance_squared_to(from_position)
    )

    # 截取指定数量
    if count > 0 and candidates.size() > count:
        candidates.resize(count)

    return candidates
```

### 3.6 全局覆盖指令流程

```
CommandSystem.issue_command(RALLY, position, -1)
  → EventBus.command_override_rally.emit(position)
  → 所有友方 CombatUnitBase 的 AIController 收到信号
  → AIController._on_rally_command(position):
      if current_task != null:
          current_task.status = OVERRIDDEN   # 原任务标记为被覆盖
          current_task = null
      # 创建一个临时的 RALLY CombatTask
      current_task = CombatTaskFactory.create(RALLY, position, unit_id)
      BehaviorFSM.switch_to(ExecuteTaskBehavior)
  → 所有单位移动到集结点
  → 到达后自动进入 GuardBehavior（原地警戒）
```

### 3.7 AIController 任务模式 vs 自主模式的行为差异

| 场景 | 任务模式 | 自主模式 |
|------|---------|---------|
| **默认行为** | 执行 CombatTask 指定的行为 | `GuardBehavior`（警戒）或 `PatrolBehavior`（游荡） |
| **遇敌** | 自卫战斗，但**不主动索敌**（完成任务优先） | 主动索敌战斗 |
| **战斗结束** | 返回执行任务 | 回到默认行为 |
| **追击距离** | 限制在任务区域半径内 | 追击范围由 `HatredSystem.chase_range` 配置 |
| **逃跑** | 任务模式不逃跑（除非全局撤退指令） | 低血量时触发 `FleeBehavior` |
| **被全局指令覆盖** | 当前任务标记 OVERRIDDEN | 直接切换到全局指令行为 |

> **自卫 vs 索敌的区别：** "自卫"意味着只攻击正在攻击自己的敌人。"索敌"意味着主动扫描并攻击警戒范围内的所有敌方单位。任务模式中单位优先完成任务，途中被攻击才还击；自主模式中单位主动巡逻并攻击任何进入视野的敌人。

### 3.8 与 FarmWorker 任务系统的对比

| 维度 | FarmWorker TaskData | CombatTask |
|------|-------------------|------------|
| **驱动方式** | 任务队列（FIFO） | 单任务（一个时刻只执行一个任务） |
| **任务来源** | 地块操作（翻耕、种植等） | 玩家战略指令（探索、守卫、攻击） |
| **任务持久性** | 排队执行，不完成不下一个 | 单任务执行中可被全局指令覆盖 |
| **中断处理** | 不可抢占 | 全局指令（RALLY/RETREAT/HOLD）可抢占 |
| **分配机制** | UnitManager.distribute_tasks() | CommandSystem → UnitSelection → UnitManager |
| **与 AI 关系** | 任务驱动全部行为 | 任务是 AI 的一种输入，无任务时 AI 自主运行 |

## 四、与 FarmWorker 的差异对比

| 维度 | FarmWorker（非战斗） | CombatUnitBase（战斗） |
|------|---------------------|----------------------|
| **继承链** | `UnitBase` | `UnitBase → CombatUnitBase` |
| **移动驱动** | Tick 逻辑步进 + `_process` 画面插值 | `_physics_process` + `move_and_slide()` |
| **碰撞** | 无物理碰撞（CollisionShape2D 可能禁用） | 有物理碰撞（单位间推挤、地形碰撞） |
| **行为驱动** | 任务队列（FIFO TaskData） | AIController（双模式：CombatTask 驱动 / 自主行为） |
| **玩家交互** | 玩家指派地块操作任务 | 玩家发高层指令，系统自动选兵+分派 |
| **攻击能力** | 无 | 有（通过 Skill 系统统一管理，普攻也是技能） |
| **受击能力** | 继承自 UnitBase.take_damage() | 有完整 hitbox/hurtbox 系统 |
| **Buff 系统** | 无 | 有（active_buffs 数组） |
| **技能系统** | 无 | 有（skills 数组 + 统一冷却管理 + 阶段推进） |
| **AI 控制器** | 无（任务系统代替决策） | 有（AIController — 仇恨/技能选择/行为状态机） |
| **任务结构** | 队列中可排多个任务 | 单任务（一个时刻只持有一个 CombatTask） |
| **指令覆盖** | 不可抢占正在执行的任务 | 全局指令（RALLY/RETREAT/HOLD）可覆盖 |
| **法力值** | 无 | 可选（max_mana > 0 时启用） |
| **工作能力** | 有（PLOW/PLANT/HARVEST/DIG） | 无（除非特殊战斗工人的混合体） |
| **选中行为** | 玩家可选中并指派任务 | 玩家可选中（友方）或不可选中（敌方） |
| **与 TileActions 交互** | 是（执行地块操作） | 否 |
| **死亡处理** | 清空任务队列 + 播放死亡动画 + 移除 | 播放死亡动画 + 移除 + 可能触发事件 |

### 关键设计决策

1. **FarmWorker 不继承 CombatUnitBase。** 农场工人不参与战斗，不需要 90% 的战斗系统属性。强行继承会导致 FarmWorker 携带大量无用字段（attack_damage、skills、hitbox 等）。

2. **但 FarmWorker 可以被攻击。** 因为 `take_damage()` 和 `faction` 在 UnitBase 中定义，FarmWorker 本身就是 "可被攻击但不会攻击" 的单位。敌方战斗单位可以将 FarmWorker 作为有效攻击目标。

3. **如果未来需要"战斗工人"**（既能种田又能战斗），可以创建一个 `CombatWorker` 类，同时继承 CombatUnitBase 并组合 FarmWorker 的任务系统——但这是远期扩展，不作为当前设计目标。
