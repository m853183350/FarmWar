> 基于 `Docs/20260624效果架构设计.md` 的设计思路，结合当前项目实际代码，给出道具/效果系统的演进方案。

## 一、现状分析

### 1.1 当前架构回顾

```
PropData (纯数据, JSON→RefCounted)
  └── prop_id, prop_name, rarity, max_stack
  └── trigger_signal: StringName     ← 监听的 EventBus 信号
  └── effects: Array[Dictionary]     ← [{type: "add_storage_item", params: {...}}]

PropManager (Node, 挂 Player 下)
  ├── props: {prop_id: count}        ← 运行时持有量
  ├── prop_library: {prop_id: PropData}
  ├── _signal_bindings               ← 信号↔道具映射
  └── _effect_manager: EffectManager
      ├── registry: {effect_type: PropEffectBase}
      ├── _context_provider: Callable  ← 返回 {storage: Storage}
      └── execute(prop_data, count, trigger_context)

PropEffectBase (RefCounted)
  ├── EffectCategory: INSTANT | MODIFIER | DURATION
  ├── execute(params, context)       ← INSTANT 子类覆写
  ├── can_trigger(params, context)   ← 条件钩子
  ├── on_apply(params, context)      ← MODIFIER/DURATION 子类覆写
  └── on_remove(params, context)     ← MODIFIER/DURATION 子类覆写
```

### 1.2 当前已实现的能力

| 能力 | 状态 | 说明 |
|------|------|------|
| INSTANT 效果（事件触发→执行） | ✅ 已实现 | sunshine_coin 验证通过 |
| 数据驱动配置（JSON） | ✅ 已实现 | 道具+效果参数全在 JSON 中 |
| 堆叠机制 | ✅ 已实现 | count 次执行 |
| 复合效果 | ✅ 已实现 | 一个道具可配多个 effects |
| 上下文注入 | ✅ 已实现 | 服务引用 + 触发数据合并 |
| 动态信号绑定 | ✅ 已实现 | 按需连接/断开 EventBus 信号 |
| MODIFIER 效果系统 | ✅ 已实现（Phase 0+1） | ModifierRegistry + Domain + target_filter，jinkela 验证通过 |
| DURATION 生命周期接口 | ⚠️ 基类已定义 | on_apply/on_remove 已声明，待 Phase 4 实现调度层 |
| 两大系统组合使用 | 📐 方案已确定 | INSTANT 事件触发 + DURATION 临时注册到 ModifierRegistry（见第十二章） |

### 1.3 当前架构的核心问题

#### 问题 1：MODIFIER 效果缺少"参与计算链"的能力

当前 MODIFIER 的 `on_apply`/`on_remove` 虽然已定义，但：
- **没有统一的"查询所有生效修饰器"的入口**。如果作物系统想计算最终产量，它不知道有哪些效果正在影响自己。
- **效果之间没有优先级**。如果两个效果都修改 `fertility`，谁先谁后？
- **修改方式不统一**。有些效果直接改 `tile_data` 字段（如 jinkela 的设计文档写 `tile.fertility_modifier_1 += 0.3`），有些可能需要改倍率。这导致被修改的数据分散在各处，难以追踪和调试。

#### 问题 2：缺乏领域（Domain）划分

当前所有效果都走同一条 `EffectManager.execute()` 通道。但实际上：
- **影响地块的效果**（肥力、产量、生长速度）需要和地块系统的属性计算绑定
- **影响仓库的效果**（容量、损耗）需要和 Storage 的数据结构绑定
- **影响商店的效果**（价格、可售列表）需要和商店系统的计算绑定
- **影响玩家的效果**（移速、采集量）需要和玩家/单位属性绑定

没有领域划分的后果：每个效果类都需要知道它要修改的具体对象和方法，效果代码与目标系统强耦合。

#### 问题 3：简单修饰器也需要写完整 GDScript 类

当前的 `ModifyTileStatEffect`（jinkela 需要）需要：
1. 创建 `modify_tile_stat_effect.gd` 文件
2. 继承 `PropEffectBase`
3. 覆写 `get_category()`、`on_apply()`、`on_remove()`
4. 在 `PropManager._setup_effect_manager()` 中注册

如果未来有 100 种道具（"玉米产量+20%""小麦生长+15%""所有作物产量+10%"…），就需要 100 个效果类文件。**这些文件的逻辑高度相似，只是参数不同。**

#### 问题 4：效果间依赖和互斥无法表达

设计文档中的 `requires` 和 `conflicts_with` 字段目前不存在。随着道具种类增多，会出现：
- 道具 A 需要道具 B 先存在才能生效
- 道具 A 和道具 C 不能同时持有
- 同类加成是叠加还是取最高？

#### 问题 5：上下文提供器扩展性差

当前 `_context_provider` 只返回 `{storage: Storage}`。每接入一个新系统（UnitManager、FarmlandManager、PathfindingManager…），就需要修改 `_provide_effect_context()` 方法。随着效果作用的领域增多，这个方法会越来越臃肿。

## 二、设计文档核心思路解读

`Docs/20260624效果架构设计.md` 提出了以下关键设计：

### 2.1 核心思想

> **效果定义和作用目标彻底解耦，按领域各自维护计算链。**

效果不再直接修改目标对象的属性，而是：
1. 向"领域"注册自己
2. 领域维护一个有序的效果链
3. 当需要计算最终值时：`base_value → Domain.calculate() → final_value`

### 2.2 关键组件

```
EffectDefinition（纯数据）
  ├── target_domains: ["tile", "player", "warehouse"]  ← 影响哪些领域
  ├── priority: int                                      ← 排序优先级
  ├── condition: Callable                                ← 触发条件
  └── calculator: Callable                               ← 计算逻辑

Domain（每个领域一个）
  ├── domain_name: String
  ├── _chain: Array[EffectDefinition]  (按 priority 排序)
  └── calculate(base_value) → final_value

EffectRegistry（全局注册中心/Autoload）
  ├── _domains: {domain_name: Domain}
  ├── register_effect(effect)
  └── get_domain(name) → Domain
```

### 2.3 标签系统思路

避免为每个效果手写 calculator，用标签组合表达常见模式：

| 标签 | 含义 |
|------|------|
| `yield_bonus` | 产量加成 |
| `growth_speed` | 生长速度 |
| `additive` | 叠加（result += base × value） |
| `multiplicative` | 乘算（result ×= 1 + value） |
| `override` | 取最高值 |

### 2.4 该方案与当前项目的差异点

| 维度 | 设计文档方案 | 当前项目 | 差异 |
|------|-------------|---------|------|
| 效果载体 | `EffectDefinition`（纯数据+Callable） | `PropEffectBase` 子类（GDScript 类） | 文档偏向数据驱动，当前偏向类驱动 |
| 触发方式 | 通过 Domain 计算链被动参与 | 通过 EventBus 信号主动触发 | 文档的 MODIFIER 是"被查询"的，当前是"被通知"的 |
| 注册机制 | 全局 Autoload EffectRegistry | PropManager 内的 EffectManager | 文档是全局的，当前是玩家级别的 |
| 代码量 | 理想情况下标签替代 calculator | 每个效果一个 GDScript 文件 | 文档更省代码 |
| 效果类型 | 未区分 INSTANT/MODIFIER | 明确三种类别 | 文档侧重 MODIFIER，忽略 INSTANT |

## 三、优化方案

### 3.1 总体策略：**保留 + 增强，而非重写**

原则：
1. **现有的 INSTANT 效果路径不动** — EventBus 触发 → EffectManager.execute() 已验证有效
2. **新增 ModifierRegistry 处理 MODIFIER 效果** — 引入 Domain + ModifierChain，解决"计算链"问题
3. **标签系统作为 MODIFIER 的简化手段** — 减少简单修饰器的代码量
4. **增强 PropData 和基础设施** — 添加 priority、requires、conflicts_with
5. **扩大上下文提供器** — 覆盖更多游戏系统

### 3.2 架构演进图

```
优化后架构：

PropManager (Node, 挂 Player 下)
  │
  ├── props / prop_library / _signal_bindings  (不变)
  │
  ├── _effect_manager: EffectManager           (处理 INSTANT 效果，不变)
  │   └── execute(prop_data, count, trigger_context)
  │       └── [AddStorageItemEffect, HealUnitEffect, ...]  ← INSTANT 效果类
  │
  └── _modifier_registry: ModifierRegistry     (新增！处理 MODIFIER 效果)
      ├── _domains: {
      │     "tile": TileDomain,
      │     "player": PlayerDomain,
      │     "warehouse": WarehouseDomain,
      │     "shop": ShopDomain,
      │     "inventory": InventoryDomain,
      │   }
      ├── register_modifier(modifier_data)     ← 道具添加时调用
      ├── unregister_modifier(modifier_data)   ← 道具移除时调用
      ├── calculate(domain, stat, base) → final  ← 游戏系统查询时调用
      └── _active_modifiers: Array             ← 所有活跃修饰器

游戏系统查询示例：
  BaseTile._calculate_fertility():
      var base := fertility_base + fertility_modifier_1
      # 新增：通过 ModifierRegistry 获取最终值
      base = PropManager.modifier_registry.calculate("tile", "fertility", base)
      return base * fertility_multiplier + fertility_modifier_2

  Crop._calculate_yield():
      var base := crop_config.base_yield
      return PropManager.modifier_registry.calculate("tile", "yield", base)
```

### 3.3 新增类设计

#### 3.3.1 ModifierRegistry（修饰器注册中心）

```gdscript
# scripts/items/modifier_registry.gd
class_name ModifierRegistry extends RefCounted

## 领域映射 {domain_name: Domain}
var _domains: Dictionary = {}

## 活跃修饰器列表（用于查询和调试）
var _active_modifiers: Array[Dictionary] = []

## 注册一个修饰器到对应领域
func register_modifier(modifier_data: Dictionary, prop_id: String, count: int) -> void:
    var target_domains: Array = modifier_data.get("target_domains", [])
    for domain_name: String in target_domains:
        var domain: Domain = _ensure_domain(domain_name)
        domain.add_modifier(modifier_data, prop_id, count)
    _active_modifiers.append({
        "prop_id": prop_id,
        "count": count,
        "modifier_data": modifier_data,
    })

## 注销修饰器
func unregister_modifier(prop_id: String) -> void:
    for domain in _domains.values():
        (domain as Domain).remove_modifier(prop_id)
    _active_modifiers = _active_modifiers.filter(
        func(d): return d.prop_id != prop_id
    )

## 查询某领域某属性的最终值
func calculate(domain_name: String, stat_name: String, base_value: float) -> float:
    var domain: Domain = _domains.get(domain_name, null) as Domain
    if domain == null:
        return base_value
    return domain.calculate(stat_name, base_value)

## 重新计算所有修饰器（当 modifier 参数变化时）
func recalculate_all() -> void:
    for domain in _domains.values():
        (domain as Domain).sort_chain()

func _ensure_domain(domain_name: String) -> Domain:
    if not _domains.has(domain_name):
        var d := Domain.new()
        d.domain_name = domain_name
        _domains[domain_name] = d
    return _domains[domain_name] as Domain

func get_active_modifiers() -> Array[Dictionary]:
    return _active_modifiers
```

#### 3.3.2 Domain（领域）

```gdscript
# scripts/items/domain.gd
class_name Domain extends RefCounted

var domain_name: String = ""
var _chain: Array[Dictionary] = []  # [{prop_id, stat, value, priority, tags, calculator}]

func add_modifier(modifier_data: Dictionary, prop_id: String, count: int) -> void:
    var stat: String = modifier_data.get("stat", "")        # 如 "fertility", "yield"
    var value: float = modifier_data.get("value", 0.0) * float(count)
    var priority: int = modifier_data.get("priority", 0)
    var tags: Array = modifier_data.get("tags", [])         # 如 ["additive", "yield_bonus"]
    var calculator: Callable = modifier_data.get("calculator", Callable())

    _chain.append({
        "prop_id": prop_id,
        "stat": stat,
        "value": value,
        "priority": priority,
        "tags": tags,
        "calculator": calculator,
    })
    sort_chain()

func remove_modifier(prop_id: String) -> void:
    _chain = _chain.filter(func(d): return d.prop_id != prop_id)

func calculate(stat_name: String, base_value: float) -> float:
    var result: float = base_value
    for modifier: Dictionary in _chain:
        if modifier.stat != stat_name:
            continue

        var value: float = modifier.get("value", 0.0)
        var tags: Array = modifier.get("tags", [])
        var calculator: Callable = modifier.get("calculator", Callable())

        # 如果有自定义 calculator，优先使用
        if calculator.is_valid():
            result = calculator.call(result)
            continue

        # 否则按标签自动计算
        if "additive" in tags:
            result += base_value * value       # 基于原始值的叠加
        elif "multiplicative" in tags:
            result *= (1.0 + value)            # 乘算
        elif "override" in tags:
            result = max(result, value)        # 取最高
        elif "flat" in tags:
            result += value                    # 固定值加成

    return result

func sort_chain() -> void:
    _chain.sort_custom(func(a: Dictionary, b: Dictionary) -> bool:
        return a.priority < b.priority
    )
```

### 3.4 PropData 增强

在现有 `PropData` 中新增字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `prop_category` | String | `"instant"`（默认） / `"modifier"` / `"duration"` |
| `modifier` | Dictionary | MODIFIER 道具的修饰器配置（含 target_domains, stat, value, tags 等） |
| `priority` | int | 全局排序优先级（默认 0） |
| `requires` | Array[String] | 前置道具 ID 列表 |
| `conflicts_with` | Array[String] | 互斥道具 ID 列表 |

### 3.5 PropManager 改造

需要在 `PropManager` 中新增/修改的逻辑：

```gdscript
# 新增成员
var _modifier_registry: ModifierRegistry = null

# _setup_effect_manager() 中新增
func _setup_modifier_registry() -> void:
    _modifier_registry = ModifierRegistry.new()

# add_prop() 中新增 MODIFIER 处理分支
func add_prop(prop_id: String) -> bool:
    # ... 现有逻辑：检查上限、增加计数、连接信号 ...

    var data: RefCounted = prop_library[prop_id]
    var category: String = data.get("prop_category", "instant")

    match category:
        "modifier":
            _apply_modifier(data, new_count)
        "instant":
            # 现有逻辑：首次添加连接信号
            if current_count == 0:
                _ensure_signal_connected(trigger_signal, prop_id)

# remove_prop() 中新增 MODIFIER 处理分支
func remove_prop(prop_id: String) -> bool:
    # ... 现有逻辑 ...

    var category: String = data.get("prop_category", "instant")
    match category:
        "modifier":
            if new_count <= 0:
                _remove_modifier(prop_id)
            else:
                # 数量减少，更新修饰器值
                _update_modifier(data, new_count)

# 新增方法
func _apply_modifier(data: RefCounted, count: int) -> void:
    var modifier_config: Dictionary = data.get("modifier", {})
    if modifier_config.is_empty():
        return
    _modifier_registry.register_modifier(modifier_config, data.get("prop_id"), count)

func _remove_modifier(prop_id: String) -> void:
    _modifier_registry.unregister_modifier(prop_id)

func _update_modifier(data: RefCounted, count: int) -> void:
    _remove_modifier(data.get("prop_id"))
    _apply_modifier(data, count)
```

### 3.6 扩大上下文提供器

当前 `_provide_effect_context()` 只返回 `{storage}`。改为注册模式：

```gdscript
## 上下文服务注册表。各系统在初始化时注册自己的引用。
var _context_services: Dictionary = {}

## 注册上下文服务（由外部系统调用）
func register_context_service(service_name: String, service_ref: Variant) -> void:
    _context_services[service_name] = service_ref

## 上下文提供器（改为从注册表读取）
func _provide_effect_context() -> Dictionary:
    return _context_services.duplicate()

# 在 _ready() 中：
func _ready() -> void:
    _cache_storage()
    register_context_service("storage", _storage)
    # 未来其他系统注册：
    # register_context_service("unit_manager", UnitManager)
    # register_context_service("farmland_manager", FarmlandManager)
```

> 好处：新增服务无需改 `_provide_effect_context()`，只需在初始化时注册一行。

### 3.7 效果依赖与互斥检查

在 `add_prop()` 和 modifier 生效前增加检查：

```gdscript
## 检查前置条件
func _check_requirements(data: RefCounted) -> bool:
    var requires: Array = data.get("requires", [])
    for req_id: String in requires:
        if not has_prop(req_id):
            return false
    return true

## 检查冲突
func _check_conflicts(data: RefCounted) -> bool:
    var conflicts: Array = data.get("conflicts_with", [])
    for conflict_id: String in conflicts:
        if has_prop(conflict_id):
            return false
    return true
```

### 3.8 领域划分

结合当前项目规划的系统，建议初期划分以下领域：

| Domain 名称 | 管辖范围 | 典型 stat（参数名，非最终值） | 查询者 |
|-------------|---------|-----------|--------|
| `tile` | 所有地块属性 | `fertility_modifier_1`, `fertility_multiplier`, `fertility_modifier_2`, `yield_modifier_1`, `yield_multiplier`, `growth_speed_mod` | BaseTile, Crop |
| `player` | 玩家自身 | `move_speed_mod`, `gather_amount_mod` | Player, UnitBase |
| `warehouse` | 仓库 | `capacity_mod`, `decay_rate_mod` | Storage |
| `shop` | 商店 | `price_multiplier`, `unlock_items` | Shop（未来） |
| `inventory` | 背包 | `slot_count_mod`, `weight_limit_mod` | Inventory（未来） |
| `unit` | 作战单位 | `attack_mod`, `defense_mod`, `speed_mod` | UnitBase（未来） |

**初期只需实现 `tile` 领域**（金坷垃需要），其他领域按需递增。

## 五、设计文档思路的取舍与改进

### 5.1 采纳的设计

| 设计文档思路 | 采纳方式 |
|-------------|---------|
| Domain 划分 | ✅ 完全采纳，作为 MODIFIER 的核心组织方式 |
| 优先级排序 | ✅ 完全采纳，Domain._chain 按 priority 排序 |
| 标签组合系统 | ✅ 采纳，但保留自定义 calculator 的出口 |
| requires / conflicts_with | ✅ 完全采纳 |
| base → Domain.calculate() → final 数据流 | ✅ 完全采纳 |

### 5.2 改进的设计

| 设计文档思路 | 改进 | 原因 |
|-------------|------|------|
| 效果只有 `EffectDefinition` 一种类型 | 保留 INSTANT / MODIFIER / DURATION 三分类 | INSTANT 效果（如 sunshine_coin）与 MODIFIER 效果（如 jinkela）触发机制完全不同，不应强行统一 |
| `calculator: Callable` | 标签自动计算 + 可选自定义 Callable | 90% 的修饰器用标签够用，但复杂效果（如"产量随持有金币数量动态变化"）仍需代码 |
| EffectRegistry 是 Autoload | ModifierRegistry 放在 PropManager 下 | 道具是玩家级别的概念，不同玩家可能持有不同道具（多人模式下），不应全局共享 |
| 一个道具跨 domain 需注册多个 EffectDefinition | 一个道具的 modifier 配置中声明 `target_domains: ["tile", "player"]` | 更简洁，一个配置搞定 |
| 所有效果都用 Domain 链计算 | INSTANT 效果继续走 EventBus + EffectManager | 事件驱动的即时效果（添加物品、生成实体）用现有的 trigger→execute 模式更自然 |

### 5.3 未被采纳的设计

| 设计文档思路 | 原因 |
|-------------|------|
| 完全用标签替代所有 calculator | 复杂效果（条件计算、动态值、多步骤操作）仍需代码实现，标签只覆盖 80% 常见场景 |
| `condition: Callable`（在 EffectDefinition 上） | 当前项目已有 `PropEffectBase.can_trigger()` 和 `trigger_condition`，MODIFIER 的筛选条件更适合用 `target_filter`（如只对 farmland 生效） |
| 一个道具绑定多个 domain 时分别创建 EffectDefinition | 增加配置复杂度。当前方案一个 modifier 对象声明 `target_domains` 数组即可 |

## 六、关键设计决策

### 决策 1：INSTANT 和 MODIFIER 的触发模型不同，不要强行统一

- **INSTANT**：事件驱动。"当 X 发生时，做 Y"。适合 EventBus 信号触发。
- **MODIFIER**：状态驱动。"只要持有，Z 属性就变"。适合 Domain 计算链。
- 两者自然不同，分开处理比强求统一更清晰。

### 决策 2：标签系统覆盖 80%，自定义类覆盖 20%

不要试图用标签覆盖所有场景。保留 `calculator: Callable` 出口，让复杂效果可以用代码实现。标签是**减少简单道具代码量**的工具，不是**替代所有效果类**的方案。

### 决策 3：ModifierRegistry 是玩家级别的，不是全局的

多人模式下，不同玩家持有不同道具。`ModifierRegistry` 放在 `PropManager`（Player 节点下）是正确的位置。未来如需全局效果（如天气影响所有玩家），再扩展全局层面。

### 决策 4：target_filter 替代 target_tile_type

设计文档的 jinkela 用 `target_tile_type: "farmland"` 来筛选。更通用的做法是 `target_filter: {tile_type: "farmland"}` 或 `target_filter: {crop_id: "wheat_tier1"}`。这让 filter 可以按任意维度筛选（地块类型、作物类型、是否有建筑等）。

### 决策 5：Domain 链是参数聚合层，不替代计算公式

**已有的底层公式（如肥力、温度、湿度）不会被改变。** 道具只影响公式中的**参数**（`修正1`、`修正2`、`地块倍率`等），不改变公式结构。

#### 关键区分

```
┌─────────────────────────────────────────────────────┐
│  Layer 2: Domain 聚合层（ModifierRegistry）          │
│  查询 "tile" 领域的 "fertility_modifier_1"          │
│  → 汇总所有影响该参数的道具，返回聚合值              │
│  例如: 金坷垃 +0.3, 肥料 +0.5 → 返回 0.8           │
└──────────────────┬──────────────────────────────────┘
                   │ 聚合后的参数值
                   ▼
┌─────────────────────────────────────────────────────┐
│  Layer 1: 计算公式（不变）                           │
│  fertility = (fertility_base + modifier_1)           │
│            × fertility_multiplier                    │
│            + modifier_2                              │
│  这是底层逻辑，稳定不变                               │
└─────────────────────────────────────────────────────┘
```

#### 参数列表（以 tile 领域为例）

| stat 名称 | 对应公式位置 | 推荐标签 | 说明 |
|-----------|-------------|---------|------|
| `fertility_modifier_1` | `(base + modifier_1)` | `flat` | 与基础值直接相加 |
| `fertility_multiplier` | `× multiplier` | `multiplicative` | 乘算因子，多个道具叠乘 |
| `fertility_modifier_2` | `+ modifier_2` | `flat` | 乘法后再加 |
| `yield_modifier_1` | 类似结构 | `flat` | 产量修正加数 |
| `yield_multiplier` | 类似结构 | `multiplicative` | 产量修正倍率 |
| `growth_speed_mod` | 生长速度 | `flat` / `multiplicative` | 按需选择 |

#### 道具配置示例（金坷垃 — 影响 modifier_1）

```json
{
    "prop_id": "jinkela",
    "prop_name": "金坷垃",
    "prop_category": "modifier",
    "modifier": {
        "target_domains": ["tile"],
        "stat": "fertility_modifier_1",
        "value": 0.3,
        "priority": 100,
        "tags": ["flat"],
        "target_filter": { "tile_type": "farmland" }
    }
}
```

#### 地块系统查询示例

```gdscript
# BaseTile._calculate_fertility()
func _calculate_fertility() -> void:
    # 基础值
    var base: float = tile_data.fertility_base

    # 从 ModifierRegistry 获取聚合后的参数
    var mod1: float = _query_modifier("fertility_modifier_1")
    var mult: float = _query_modifier("fertility_multiplier", tile_data.fertility_multiplier)
    var mod2: float = _query_modifier("fertility_modifier_2")

    # 公式不变
    tile_data.fertility = (base + mod1) * mult + mod2

func _query_modifier(stat_name: String, default: float = 0.0) -> float:
    var pm: Node = get_node_or_null("/root/.../PropManager")  # 或通过其他方式获取引用
    if pm == null:
        return default
    return pm.modifier_registry.calculate("tile", stat_name, default)
```

#### 几个道具叠加的完整示例

假设玩家同时持有 3 个道具：

| 道具 | stat | value | tags | 堆叠数 |
|------|------|-------|------|--------|
| 金坷垃 | `fertility_modifier_1` | 0.3 | `flat` | 2 |
| 月光粉 | `fertility_multiplier` | 0.15 | `multiplicative` | 1 |
| 深耕剂 | `fertility_modifier_2` | 0.5 | `flat` | 3 |

查询时：
- `calculate("tile", "fertility_modifier_1", 0.0)` → `0.0 + 0.3×2 = 0.6`
- `calculate("tile", "fertility_multiplier", 0.8)` → `0.8 × (1.0 + 0.15×1) = 0.92`
- `calculate("tile", "fertility_modifier_2", 0.0)` → `0.0 + 0.5×3 = 1.5`

最终公式：`fertility = (base + 0.6) × 0.92 + 1.5`

> **核心要点**：Domain 链只负责回答 "modifier_1 现在是多少？multiplier 现在是多少？" 这类聚合问题。公式结构完全由各自的游戏系统（BaseTile, Crop 等）维护，不进入 Domain 层。

## 九、方案对比 — 为什么这样做

### 如果不改，会遇到什么问题？

当道具数量达到 30+ 时：

1. **`scripts/items/effects/` 下会有 30+ 个文件**，其中 80% 是高度相似的简单修饰器
2. **PropManager._setup_effect_manager() 会有 30+ 行注册代码**
3. **调试困难** — 想知道"当前对地块 fertility 生效的所有效果"需要遍历所有效果类
4. **计算不一致** — 有些效果直接改 tile_data 字段，有些走其他路径，难以保证计算顺序和一致性
5. **新系统接入困难** — 每次加新效果目标（如商店系统），需要改 PropManager 和 EffectManager

### 优化后的收益

1. **简单修饰器零代码** — 90% 的 "X属性 +Y%" 道具只需 JSON 配置
2. **效果可查询** — `ModifierRegistry.get_active_modifiers()` 可列出所有活跃效果
3. **计算可预测** — 所有对同一 stat 的修饰器走同一条 Domain 链，顺序由 priority 控制
4. **新领域易扩展** — 新增 shop domain 时，只需在 ModifierRegistry 中新增一个 Domain 实例，不需要改其他代码
5. **与现有系统兼容** — INSTANT 效果路径完全保留，sunshine_coin 不受影响

## 十、风险评估

| 风险 | 等级 | 缓解措施 |
|------|------|---------|
| MODIFIER 效果与 INSTANT 效果的管理分离可能导致概念混乱 | 低 | 文档明确区分，PropData.prop_category 字段自文档化 |
| Domain.calculate() 的性能（每帧可能被多次调用） | 低 | 修饰器数量通常 < 100，线性遍历开销可忽略；后续可加缓存 |
| 标签系统的计算逻辑可能过于简化 | 中 | 保留 `calculator: Callable` 出口，复杂情况可降级到自定义类 |
| 新老道具格式共存维护成本 | 低 | sunshine_coin 格式完全不动，新 MODIFIER 道具用新格式，互不干扰 |

## 十一、总结

本方案的核心改动可以归纳为三句话：

1. **MODIFIER 效果从"主动推送"改为"被动查询"** — 效果不再直接修改对象属性，而是向 Domain 注册自己；需要计算最终值时，由目标系统主动查询 Domain 链。
2. **标签系统让 80% 的简单修饰器不需要写代码** — `additive`/`multiplicative`/`flat`/`override` 四种标签覆盖绝大多数场景。
3. **INSTANT 效果路径不变** — 已有的 sunshine_coin 和 EventBus 触发机制不改造，新系统是增量而非替换。

这样既吸收了设计文档"领域解耦 + 标签简化"的核心思想，又保持了与现有代码的兼容性。

## 十二、两大系统组合模式

### 12.1 问题

EffectManager（事件驱动 INSTANT 效果）和 ModifierRegistry（被动查询 MODIFIER 效果）是否可以组合使用？

具体场景：道具监听某个 EventBus 事件 → 给 Domain 临时添加修饰器 → 持续一段时间后自动移除。这是 DURATION 类别的典型需求。

### 12.2 答案：可以，且是设计上刻意预留的结合点

两个系统解决的是不同维度的问题，天然互补：

| 系统 | 触发方式 | 擅长的事 |
|------|---------|---------|
| **EffectManager** | 事件驱动（"当 X 发生时"） | 监听信号、条件评估、冷却控制、堆叠执行 |
| **ModifierRegistry** | 被动查询（"Y 属性现在是多少"） | 多来源聚合、优先级排序、标签计算、target_filter 过滤 |

### 12.3 推荐模式：通用 DURATION 效果类

不为每种"事件→临时修饰器"写独立文件。用一个**通用**的 `ApplyTimedModifierEffect`（DURATION 类别）覆盖所有同类道具：

```
道具 JSON 配置（零代码）:
{
  "prop_id": "moonlight_blessing",
  "prop_category": "duration",
  "trigger_signal": "crop_harvested",
  "effects": [{
    "type": "apply_timed_modifier",
    "params": {
      "modifier_config": {
        "target_domains": ["tile"],
        "stat": "fertility_multiplier",
        "value": 0.3,
        "priority": 50,
        "tags": ["multiplicative"]
      },
      "duration_ticks": 600
    }
  }]
}

EffectManager（事件触发 + 生命周期管理）:
  on_apply  → ModifierRegistry.register_modifier()
  (持续 N 个 tick)
  on_remove → ModifierRegistry.unregister_modifier()
```

**效果类的核心逻辑**（一个类覆盖所有场景）：

```gdscript
class_name ApplyTimedModifierEffect extends PropEffectBase

func get_category() -> EffectCategory:
    return EffectCategory.DURATION

func on_apply(params: Dictionary, context: Dictionary) -> void:
    var pm: PropManager = context["prop_manager"]
    pm.get_modifier_registry().register_modifier(
        params["modifier_config"],
        params["prop_id"],
        params.get("count", 1)
    )

func on_remove(params: Dictionary, context: Dictionary) -> void:
    var pm: PropManager = context["prop_manager"]
    pm.get_modifier_registry().unregister_modifier(params["prop_id"])
```

### 12.4 为什么这比写独立效果类更好

1. **零新文件** — "作物收获后产量临时+30%" 这类道具只需 JSON，不需要新 GDScript
2. **复用现有轮子** — 事件监听走 EffectManager（已成熟），属性聚合走 ModifierRegistry（已实现），效果类只是桥接
3. **调度层集中** — 所有限时效果的计时和到期清理由 EffectManager 一处管理
4. **与 MODIFIER 统一** — 临时修饰器和永久修饰器（如 jinkela）走同一条 Domain 计算链，基底公式不受影响

### 12.5 还需要的 Phase 4 工作

1. **EffectManager 增加 DURATION 调度** — 维护活跃 DURATION 效果列表，TickSystem 每 tick 检查到期
2. **上下文注入 PropManager 引用** — 让效果能访问 ModifierRegistry（注册上下文服务即可）
3. **PropManager 联动清理** — `remove_prop` 时调用 `on_remove` 注销临时修饰器

|------|---------|------------|---------|
| 月光祝福 | 收获作物时触发 | 所有耕地肥力倍率 +30% | 600 tick 后自动移除 |
| 加速生长 | 作物成熟时触发 | 指定地块生长速度 ×2 | 300 tick 后自动移除 |
| 临时护盾 | 受到攻击时触发 | 单位防御 +50% | 200 tick 后自动移除 |

核心原则：**事件触发（EventBus） → 临时注册（ModifierRegistry） → 到期自动注销（TickSystem）**

### 13.2 核心设计：DurationTracker

新增 **DurationTracker** 类，担任 DURATION 效果的**调度层**。它不关心效果的具体逻辑，只负责计时和到期通知。

```
DurationTracker (RefCounted, 由 EffectManager 持有)
  │
  ├── _active_effects: Array[Dictionary]
  │     每个条目:
  │     {
  │       "instance_id": int,           # 唯一 ID（自增）
  │       "prop_id": String,            # 来源道具 ID
  │       "effect_type": StringName,    # 效果类型（如 "apply_timed_modifier"）
  │       "effect_instance": PropEffectBase,  # 效果实例（到期时调 on_remove）
  │       "params": Dictionary,         # 效果参数（含 modifier_config + duration_ticks）
  │       "context": Dictionary,        # 触发时的运行时上下文
  │       "remaining_ticks": int,       # 剩余 tick 数
  │       "total_ticks": int,           # 总 tick 数（用于 UI 进度显示）
  │     }
  │
  ├── register(effect_instance, params, context, duration_ticks, prop_id) → int
  │     注册一个限时效果，返回 instance_id
  │
  ├── unregister(instance_id) → bool
  │     手动提前终止（调用 on_remove 后移除）
  │
  ├── unregister_by_prop(prop_id: String) → int
  │     清理指定道具的所有活跃 DURATION 效果，返回清理数量
  │
  ├── _on_tick(delta: float) → void
  │     每 tick 对所有活跃效果递减 remaining_ticks，到期时调 _expire()
  │
  ├── _expire(entry: Dictionary) → void
  │     调用 effect_instance.on_remove()，从活跃列表移除，发射信号
  │
  ├── get_active_for_prop(prop_id: String) → Array[Dictionary]
  │     查询指定道具的活跃 DURATION 效果（调试用）
  │
  ├── get_all_active() → Array[Dictionary]
  │     获取所有活跃 DURATION 效果（调试面板用）
  │
  └── is_tracking(instance_id: int) → bool
```

#### 13.2.1 核心逻辑伪代码

```gdscript
# scripts/items/duration_tracker.gd
class_name DurationTracker extends RefCounted

## 活跃 DURATION 效果列表
var _active_effects: Array[Dictionary] = []

## 自增 ID 计数器
var _next_instance_id: int = 0

## 已连接到 TickSystem？
var _tick_connected: bool = false

## 注册一个限时效果
func register(effect_instance: PropEffectBase, params: Dictionary, context: Dictionary,
              duration_ticks: int, prop_id: String) -> int:
    if duration_ticks <= 0:
        push_warning("DurationTracker: duration_ticks <= 0，效果立即到期")
        effect_instance.on_remove(params, context)
        return -1

    var instance_id: int = _next_instance_id
    _next_instance_id += 1

    _active_effects.append({
        "instance_id": instance_id,
        "prop_id": prop_id,
        "effect_type": params.get("type", ""),
        "effect_instance": effect_instance,
        "params": params,
        "context": context,
        "remaining_ticks": duration_ticks,
        "total_ticks": duration_ticks,
    })

    _ensure_tick_connected()
    print("DurationTracker: 注册 DURATION 效果 #%d — prop=%s, ticks=%d" % [instance_id, prop_id, duration_ticks])
    return instance_id

## 提前终止指定效果
func unregister(instance_id: int) -> bool:
    for i: int in range(_active_effects.size()):
        var entry: Dictionary = _active_effects[i]
        if entry["instance_id"] == instance_id:
            _call_on_remove(entry)
            _active_effects.remove_at(i)
            _check_empty()
            return true
    return false

## 清理某道具的所有活跃 DURATION 效果（当道具被移除时调用）
func unregister_by_prop(prop_id: String) -> int:
    var removed: int = 0
    var i: int = _active_effects.size() - 1
    while i >= 0:
        var entry: Dictionary = _active_effects[i]
        if entry["prop_id"] == prop_id:
            _call_on_remove(entry)
            _active_effects.remove_at(i)
            removed += 1
        i -= 1
    if removed > 0:
        _check_empty()
    return removed

## TickSystem 回调 — 每 tick 递减并检查到期
func _on_tick(_delta: float) -> void:
    var expired: Array[int] = []  # 收集到期 instance_id
    var i: int = _active_effects.size() - 1
    while i >= 0:
        var entry: Dictionary = _active_effects[i]
        var remaining: int = entry["remaining_ticks"] as int - 1
        if remaining <= 0:
            _call_on_remove(entry)
            expired.append(entry["instance_id"] as int)
            _active_effects.remove_at(i)
        else:
            entry["remaining_ticks"] = remaining
        i -= 1
    _check_empty()

## 调用效果的 on_remove（安全包装）
func _call_on_remove(entry: Dictionary) -> void:
    var effect_instance: PropEffectBase = entry["effect_instance"] as PropEffectBase
    var params: Dictionary = entry["params"] as Dictionary
    var context: Dictionary = entry["context"] as Dictionary
    effect_instance.on_remove(params, context)

## 确保已连接 TickSystem
func _ensure_tick_connected() -> void:
    if _tick_connected:
        return
    if TickSystem:
        TickSystem.tick_elapsed.connect(_on_tick)
        _tick_connected = true

## 当活跃列表清空时断开 TickSystem 连接（节省开销）
func _check_empty() -> void:
    if _active_effects.is_empty() and _tick_connected:
        if TickSystem:
            TickSystem.tick_elapsed.disconnect(_on_tick)
        _tick_connected = false

## 查询方法（调试用）
func get_active_for_prop(prop_id: String) -> Array[Dictionary]:
    var result: Array[Dictionary] = []
    for entry: Dictionary in _active_effects:
        if entry["prop_id"] == prop_id:
            result.append(entry)
    return result

func get_all_active() -> Array[Dictionary]:
    return _active_effects
```

#### 13.2.2 设计要点

**① 懒连接 TickSystem。** DurationTracker 在首次 `register()` 时连接 `TickSystem.tick_elapsed`，在活跃列表清空时断开。避免空转开销。

**② 到期时批量处理。** 在遍历中直接调用 `on_remove` 并移除。遍历顺序从后往前（安全删除）。

**③ 20 tick/s × 活跃效果数。** 假设同时有 50 个活跃 DURATION 效果，每 tick 遍历 50 个条目，开销可忽略。后续可优化为按剩余 tick 数分桶（类似时间轮算法），当前规模不需要。

**④ instance_id。** 自增 int，用于外部精确追踪/取消特定效果实例。虽当前主要是 `unregister_by_prop` 场景，但预留单实例控制能力。

### 13.3 EffectManager 扩展

EffectManager 当前在 `_execute_single_effect` 的 `DURATION` 分支只调了 `on_apply`，没有持久化追踪。需要新增 DurationTracker 并完善 DURATION 分支。

#### 13.3.1 变更点

```gdscript
# EffectManager 新增成员
var _duration_tracker: DurationTracker = null

func _init() -> void:
    _duration_tracker = DurationTracker.new()

# _execute_single_effect 的 DURATION 分支改为：
func _execute_single_effect(effect_entry: Dictionary, count: int, context: Dictionary, prop_data: RefCounted) -> void:
    # ... 现有逻辑 ...

    match category:
        PropEffectBase.EffectCategory.INSTANT:
            # 不变

        PropEffectBase.EffectCategory.MODIFIER:
            # 不变

        PropEffectBase.EffectCategory.DURATION:
            # 新逻辑：先调 on_apply，再注册到 DurationTracker
            var prop_id: String = prop_data.get("prop_id") as String
            var duration_ticks: int = params.get("duration_ticks", 0) as int

            # on_apply 让效果立即生效（如注册临时修饰器到 ModifierRegistry）
            effect_instance.on_apply(params, context)

            # 注册到 DurationTracker，到期时自动调 on_remove
            _duration_tracker.register(effect_instance, params, context, duration_ticks, prop_id)

# 新增公开方法
func cleanup_duration_for_prop(prop_id: String) -> int:
    """当道具被移除时，清理其所有活跃 DURATION 效果"""
    return _duration_tracker.unregister_by_prop(prop_id)

func get_active_durations() -> Array[Dictionary]:
    """获取所有活跃 DURATION 效果（调试面板用）"""
    return _duration_tracker.get_all_active()
```

#### 13.3.2 为什么 `on_apply` 在 DurationTracker.register 之前调用

`on_apply` 是效果**立即生效**的入口（如向 ModifierRegistry 注册临时修饰器）。DurationTracker 只管理**到期时机**。两者职责不同，不应合并。

如果 `on_apply` 失败（抛异常），不应进入 DurationTracker。但当前 GDScript 无 try/catch，可在 `on_apply` 中返回 bool 表示成功与否（可选优化）。

### 13.4 通用 DURATION 效果类：ApplyTimedModifierEffect

这是 Phase 4 的**核心效果类**，桥接 EventBus 事件触发和 ModifierRegistry 临时修饰。

#### 13.4.1 设计思路

一个类覆盖所有"事件 → 临时修饰器 → 自动到期"场景。不同道具通过 JSON 配置区分，不需要每个道具写一个 GDScript 文件。

```gdscript
# scripts/items/effects/apply_timed_modifier_effect.gd
class_name ApplyTimedModifierEffect extends PropEffectBase

## 效果类别：DURATION
func get_category() -> EffectCategory:
    return EffectCategory.DURATION

## 生效时：从上下文获取 PropManager，将 modifier_config 临时注册到 ModifierRegistry
func on_apply(params: Dictionary, context: Dictionary) -> void:
    var pm: PropManager = context.get("prop_manager") as PropManager
    if pm == null:
        push_error("ApplyTimedModifierEffect: context 中缺少 prop_manager 引用")
        return

    var modifier_config: Dictionary = params.get("modifier_config", {}) as Dictionary
    if modifier_config.is_empty():
        push_error("ApplyTimedModifierEffect: params 中缺少 modifier_config")
        return

    var prop_id: String = params.get("prop_id", "") as String
    var count: int = params.get("count", 1) as int

    # 临时注册到 ModifierRegistry
    var mr: ModifierRegistry = pm.get_modifier_registry()
    mr.register_modifier(modifier_config, prop_id, count)

    # 通知外部系统重算
    pm._notify_modifiers_changed()

## 到期时：从 ModifierRegistry 注销临时修饰器
func on_remove(params: Dictionary, context: Dictionary) -> void:
    var pm: PropManager = context.get("prop_manager") as PropManager
    if pm == null:
        return

    var prop_id: String = params.get("prop_id", "") as String

    var mr: ModifierRegistry = pm.get_modifier_registry()
    mr.unregister_modifier(prop_id)

    # 通知外部系统重算
    pm._notify_modifiers_changed()
```

> **注意**：`PropManager._notify_modifiers_changed()` 当前是私有方法。实现阶段需决定是改为公开方法，还是在 PropManager 上新增一个公开的 `notify_modifiers_changed()`。

#### 13.4.2 通用性分析

这个类可以覆盖以下所有场景（只改 JSON 配置）：

| 道具概念 | modifier_config 差异 | 其他都一样 |
|---------|---------------------|-----------|
| 收获后产量临时+30% | stat: "yield_multiplier", tags: ["multiplicative"], value: 0.3 | ✅ |
| 作物成熟后生长加速 | stat: "growth_speed_mod", tags: ["flat"], value: 0.5 | ✅ |
| 受到攻击后防御提升 | target_domains: ["unit"], stat: "defense_mod" | ✅ |
| 全局肥力临时翻倍 | target_filter: {}, stat: "fertility_multiplier" | ✅ |

**未来扩展**：如果出现复杂 DURATION 效果（如"持续期间每 tick 触发一次 INSTANT 效果"），可以新建专用效果类继承 `PropEffectBase` 并覆写 `on_apply`/`on_remove`，同时 DurationTracker 的 `_on_tick` 可增加 `on_tick` 回调钩子。

### 13.8 完整生命周期流程

以"月光祝福"为例：

```
时间线 ──────────────────────────────────────────────────────────→

① 玩家获得道具
   PropManager.add_prop("moonlight_blessing")
   └→ category="duration" → 连接 EventBus.crop_harvested 信号

② 事件触发（玩家收获作物）
   EventBus.crop_harvested 信号发射
   └→ PropManager._on_crop_harvested()
       └→ _process_trigger("crop_harvested", context)
           └→ EffectManager.execute(prop_data, count, context)
               └→ _execute_single_effect(effect_entry, count, context, prop_data)
                   └→ category=DURATION:
                       ├→ ApplyTimedModifierEffect.on_apply(params, context)
                       │   ├→ ModifierRegistry.register_modifier(modifier_config, prop_id, count)
                       │   │   └→ Domain.add_modifier(...)  → 链中新增临时修饰器
                       │   └→ PropManager._notify_modifiers_changed()
                       │       └→ EventBus.tile_modifiers_changed.emit()
                       │           └→ BaseTile._calculate_fertility() 重算（含临时加成）
                       │
                       └→ DurationTracker.register(effect, params, context, 600, prop_id)
                           └→ 连接 TickSystem.tick_elapsed

③ 持续期间（tick 1 ~ 599）
   每次 TickSystem.tick_elapsed:
   └→ DurationTracker._on_tick()
       └→ remaining_ticks: 599 → 598 → ... → 1
       （不触发 on_remove，临时修饰器持续生效）

④ 到期（tick 600）
   TickSystem.tick_elapsed:
   └→ DurationTracker._on_tick()
       └→ remaining_ticks: 1 → 0 → _expire()
           └→ ApplyTimedModifierEffect.on_remove(params, context)
               ├→ ModifierRegistry.unregister_modifier(prop_id)
               │   └→ Domain.remove_modifier(...)  → 链中移除临时修饰器
               └→ PropManager._notify_modifiers_changed()
                   └→ EventBus.tile_modifiers_changed.emit()
                       └→ BaseTile._calculate_fertility() 重算（无临时加成）

⑤ 清理
   DurationTracker 检查活跃列表为空 → 断开 TickSystem.tick_elapsed
```

### 13.9 边界情况处理

#### 13.9.1 重复触发（效果尚未到期时再次触发）

| 策略 | 行为 | 适用场景 |
|------|------|---------|
| **刷新（默认）** | 终止旧实例，创建新实例（duration 重置） | 绝大多数 buff 类道具 |
| 忽略 | 旧实例仍存活时不创建新实例 | 限制类效果（如"每场战斗最多触发一次"） |
| 叠加 | 创建独立新实例，多个实例并行存在 | 可堆叠的临时效果 |

默认采用**刷新**策略。由 `ApplyTimedModifierEffect.on_apply()` 中先调 `unregister_modifier` 再 `register_modifier` 实现：

```gdscript
func on_apply(params: Dictionary, context: Dictionary) -> void:
    # ...
    # 先清理旧修饰器（如果存在），再注册新的
    mr.unregister_modifier(prop_id)
    mr.register_modifier(modifier_config, prop_id, count)
    # ...
```

DurationTracker 端同理：`register()` 前先 `unregister_by_prop(prop_id)`：

```gdscript
# EffectManager._execute_single_effect 的 DURATION 分支
match category:
    PropEffectBase.EffectCategory.DURATION:
        # 刷新策略：先清理同道具的旧效果
        _duration_tracker.unregister_by_prop(prop_id)
        effect_instance.on_apply(params, context)
        _duration_tracker.register(effect_instance, params, context, duration_ticks, prop_id)
```

如需其他策略，后续可在 `params` 中添加 `retrigger_policy: "refresh" | "ignore" | "stack"` 字段。

#### 13.9.2 道具被提前移除

玩家失去道具（`remove_prop` → count 归零）时，需清理所有活跃 DURATION 效果：

```
PropManager.remove_prop("moonlight_blessing")
└→ category="duration" → new_count=0
    ├→ EffectManager.cleanup_duration_for_prop("moonlight_blessing")
    │   └→ DurationTracker.unregister_by_prop("moonlight_blessing")
    │       ├→ ApplyTimedModifierEffect.on_remove()  # 注销临时修饰器
    │       └→ PropManager._notify_modifiers_changed()
    │
    └→ _remove_signal_binding("crop_harvested", "moonlight_blessing")
```

**关键**：`cleanup_duration_for_prop` 在 `_remove_signal_binding` 之前调用，确保临时修饰器先被注销（地块属性先恢复正常），再断开信号。

#### 13.9.3 游戏暂停/恢复

TickSystem 已内置暂停机制。`TickSystem.pause()` 后 `tick_elapsed` 不再发射，DurationTracker 的 `_on_tick` 不会被调用。恢复后正常递减。

**无需额外处理。**

#### 13.9.4 场景切换/游戏结束

当 `PropManager._exit_tree()` 被调用时：
- `_disconnect_all_signals()` 断开所有 EventBus 信号绑定
- DurationTracker 需要在 EffectManager 析构时清理（GDScript RefCounted 自动析构）
- `_exit_tree()` 中可增加显式清理：遍历所有活跃 DURATION 效果，调 `on_remove` 注销临时修饰器

```gdscript
# EffectManager 新增清理方法
func cleanup_all_durations() -> void:
    for entry: Dictionary in _duration_tracker.get_all_active():
        var effect_instance: PropEffectBase = entry["effect_instance"] as PropEffectBase
        var params: Dictionary = entry["params"] as Dictionary
        var context: Dictionary = entry["context"] as Dictionary
        effect_instance.on_remove(params, context)
    _duration_tracker = DurationTracker.new()  # 重置

# PropManager._exit_tree() 中调用
func _exit_tree() -> void:
    if _effect_manager != null:
        _effect_manager.cleanup_all_durations()
    _disconnect_all_signals()
```

#### 13.9.5 多个 DURATION 效果同时修改同一 stat

与 MODIFIER 道具的处理方式完全一致——都走 `Domain.calculate()` 的同一计算链。临时修饰器和永久修饰器（如 jinkela）在 Domain 链中**平等排序**，由 priority 控制先后顺序。

**无需额外处理。** 这正是两大系统组合使用的核心优势。

### 13.10 调试支持

#### 13.10.1 DebugUI 集成

在 `PropManager._update_debug_info()` 中新增 DurationTracker 信息：

```gdscript
# 在 _update_debug_info() 末尾新增
if _effect_manager != null:
    var active_durs: Array[Dictionary] = _effect_manager.get_active_durations()
    debug_str += "\nDurationTracker (%d active):\n" % active_durs.size()
    if active_durs.is_empty():
        debug_str += "  (none)\n"
    else:
        for entry: Dictionary in active_durs:
            var total: int = entry.get("total_ticks", 0) as int
            var remaining: int = entry.get("remaining_ticks", 0) as int
            var pct: int = int(float(remaining) / float(total) * 100.0) if total > 0 else 0
            debug_str += "  [%s] %s: %d/%d ticks (%d%%)\n" % [
                entry.get("prop_id"),
                entry.get("effect_type"),
                remaining,
                total,
                pct,
            ]
```

### 13.11 阶段 4 实施后的效果类别总览

| 类别 | 触发方式 | 生命周期管理 | 效果载体 |
|------|---------|------------|---------|
| **INSTANT** | EventBus 信号 → EffectManager.execute() | 无（执行完即结束） | `PropEffectBase.execute()` 子类 |
| **MODIFIER** | 持有期间持续生效 | PropManager add_prop/remove_prop | ModifierRegistry → Domain 链 |
| **DURATION** | EventBus 信号 → EffectManager.execute() → DurationTracker | TickSystem 驱动到期 + PropManager remove_prop 提前终止 | `PropEffectBase.on_apply()` + `on_remove()` + DurationTracker |

### 13.13 与现有系统的兼容性

| 现有系统 | 影响 | 说明 |
|---------|------|------|
| INSTANT 效果（sunshine_coin） | 无影响 | DURATION 走独立调度通道 |
| MODIFIER 效果（jinkela） | 无影响 | 临时修饰器和永久修饰器在 Domain 链中平等共存 |
| ModifierRegistry | 无改动 | DURATION 通过 EffectManager 间接使用，API 不变 |
| Domain | 无改动 | 不区分修饰器来源（永久/临时），统一排序计算 |
| EventBus | 无改动 | DURATION 使用现有信号机制 |
| TickSystem | 无改动 | DurationTracker 作为普通监听者连接 `tick_elapsed` |
| 存档系统（未来） | 需考虑 | 存档时需序列化 DurationTracker 的活跃效果列表及其 remaining_ticks |
