## 一、Autoload 设计问题

### 1.1 UnitManager 位置不符合目录规范

**问题**：`UnitManager` 位于 `scripts/units/unit_manager.gd`，但在 `project.godot` 中注册为 Autoload。按 `Docs/目录结构.md` 的设计，所有 Autoload 脚本应统一放在 `scripts/autoload/` 下。

**影响**：目录结构不一致，新开发者查找 Autoload 时需要在两个目录间跳转。

**建议**：将 `unit_manager.gd` 移动到 `scripts/autoload/`，或修改目录结构文档明确允许子系统内的 Autoload。

### 1.2 Autoload 设计与实际严重不符

**文档规划**（`Docs/目录结构.md`）列出以下 Autoload：
- `game_state.gd` — 全局游戏状态管理（**不存在**）
- `resource_manager.gd` — 资源管理器（**不存在**）
- `data_manager.gd` — 数据/存档管理（**不存在**）
- `audio_manager.gd` — 音频管理（**不存在**）
- `config.gd` — 全局配置常量（**不存在**）
- `debug_console.gd` — 调试控制台（**不存在**）

**实际注册**的 Autoload：
- `TickSystem` — 已实现
- `EventBus` — 已实现
- `TileActions` — **不在原设计中**
- `GatherActions` — **不在原设计中**
- `FarmlandManager` — **不在原设计中**
- `UnitManager` — **不在原设计中**
- `PathfindingManager` — **不在原设计中**
- `DebugOverlay` / `DebugOverlayLeft` / `DebugUI` — 替代了原设计的 `debug_console`

**影响**：设计文档与实际代码长期脱节，设计文档失去了作为开发指南的价值。

**建议**：立即更新 `Docs/目录结构.md` 的 Autoload 清单以匹配实际实现，同时评估缺失的 Autoload（如 `game_state`、`audio_manager`）是否需要补充。

### 1.3 多线程架构的复杂性

**问题**：`TickSystem` 和 `PathfindingManager` 各使用一个独立 `Thread`，增加了调试和错误处理的复杂度：
- Godot 4.x 的脚本级 Thread API 在部分平台有稳定性问题
- `call_deferred` 调度可能因节点释放导致空引用
- 两个线程的协调（信号背压 + 信号 drain）增加了理解和维护成本
- 当前地图规模（32×32）和单位数量（~10）下，线程收益几乎为零

**建议**：考虑短期使用 `Timer` 或 `SceneTreeTimer` 替代 Thread 实现 TickSystem，待游戏规模确认需线程后再引入。寻路可先改用分帧 A*（跨多个 tick 执行），消除第二个线程。

## 二、事件总线问题

### 2.1 EventBus 信号过多且无命名空间

**当前状态**：`EventBus` 包含 21 个信号，全部平铺在顶层，涵盖：
- 地形事件（`terrain_generated`、`terrain_changed`）
- 地块交互（`tile_clicked`、`tile_action_triggered`、`crop_harvest_requested`）
- 作物事件（`crop_stage_changed`、`crop_matured`、`crop_harvested`）
- 工人事件（`worker_task_completed`、`worker_state_changed`、`worker_queue_empty`）
- UI 事件（`mode_changed`）
- 采集事件（`gather_action_triggered`）
- 分配事件（`farmland_assigned`、`farmland_unassigned`）

**影响**：随着系统增多（预计 11+ 个系统），信号数量将突破 50+，新开发者难以查找和理解。任何系统连接 `EventBus` 都会触发所有信号的查找开销。

**建议**：
1. 按领域拆分为子 EventBus（如 `WorldEvents`、`CropEvents`、`UnitEvents`、`UIEvents`）
2. 或使用信号分组命名约定（如 `world:terrain_generated`），并在文档中分类

## 三、代码结构问题

### 3.1 JSON 加载代码大量重复

**问题**：以下脚本各自实现了几乎完全相同的 JSON 加载逻辑（`FileAccess.open → get_as_text → JSON.parse`）：
- `GatherActions._load_config()`
- `TileActions._load_config()`
- `PathfindingManager._load_cost_config()`
- `ModeSelector._load_config()`
- `Storage._load_catalog()`
- `TerrainGenerator._load_config()`

**已有工具**：`scripts/utils/json_loader.gd` 提供了 `JsonConfigLoader.load_config_file()`，但未被统一使用。`FarmWorker` 使用了它，但 `Storage`、`ModeSelector` 等仍在手动加载。

**建议**：所有 JSON 配置加载统一使用 `JsonConfigLoader`，或将其升级为 Autoload 提供 `load_json(path) -> Dictionary` 静态方法。

### 3.2 地块类型映射分散在多处

**问题**：地块类型（DIRT=0, STONE=1, OCEAN=2, FARMLAND=3）的映射逻辑重复出现在：
- `FarmlandManager._get_tile_type()` — 注释说明 `DIRT=0, STONE=1, OCEAN=2, FARMLAND=3`
- `TerrainGenerator._key_to_tile_type()` — match 语句映射 key → TileType
- `PathfindingManager._tile_type_to_key()` — match 语句映射 int → string
- `TileActions._try_plant_crop()` — 魔法数字 `if tile_data.tile_type != 3`

虽然 `TileInfo` 已定义了 `TileType` 枚举，但多个地方仍使用整数比较，且 key↔type 的字符串映射各自维护。

**建议**：在 `TileInfo` 中增加静态辅助方法 `to_key(type: int) -> String` 和 `from_key(key: String) -> int`，所有模块统一调用。

### 3.3 world 节点缓存多处重复

**问题**：多个 Autoload 各自维护 `_world_cache` 并实现 `_resolve_world()`：
- `FarmlandManager._resolve_world()`
- `TileActions._resolve_world()`

虽然都委托到 `WorldUtils.get_world()`，但缓存逻辑重复。

**建议**：由 `WorldUtils` 统一提供缓存机制（已提供 `get_world()`，使用方可自行缓存），Autoload 内部不再重复实现缓存。

### 3.4 Crop._get_grid_position() 通过解析节点名获取坐标

**问题**：`Crop._get_grid_position()` 通过 `tile.name.split("_")` 解析地块节点名（`tile_X_Y`）来获取网格坐标。

```gdscript
var tile_name: String = tile.name
if tile_name.begins_with("tile_"):
    var parts: PackedStringArray = tile_name.split("_")
    return Vector2i(int(parts[1]), int(parts[2]))
```

**风险**：如果地块命名规则变更（如改为 `cell_X_Y` 或增加后缀），所有作物将无法获取坐标。

**建议**：直接调用 `tile.get_grid_position()`，该方法已在 `BaseTile` 中实现。

## 四、架构设计问题

### 4.1 TerrainGenerator 职责过重

**问题**：`TerrainGenerator` 挂载在 `world` 节点上，同时承担以下职责：
1. 地形随机生成（`_generate_all_random`）
2. 配置文件加载
3. 地块节点实例化
4. 事件分发（`_on_tile_action_triggered` 将 UI 操作分发到 TileActions）
5. 作为 `world` group 的锚点

事件分发逻辑（`_on_tile_action_triggered`）属于 UI→游戏世界的中转，不应由地形生成器承担。

**建议**：
- 将 `_on_tile_action_triggered` 的处理移到独立的中间层（如新建 `WorldManager` 或由 `TileActions` 直接监听）
- 或将 `TerrainGenerator` 脚本从 `world` 根节点移除，改为挂载在 `WorldManager` 下

### 4.2 深继承与"组合优于继承"原则冲突

**问题**：`Docs/代码规范.md` 明确要求"组合优于继承"，但当前架构以深继承为主：
- `FarmWorker → UnitBase → CharacterBody2D`
- `WheatTier1 → Crop → Sprite2D`
- `DirtTile / FarmlandTile / StoneTile / OceanTile → BaseTile → Sprite2D`

继承链的优点是代码复用，缺点是：
- 基类修改影响所有子类
- 难以 mix-in 跨领域功能（如某个 Crop 需要特殊的动画行为）
- 不符合已声明的设计原则

**已有组合案例**：`AnimationController` 和 `AudioController` 作为子节点组件是正确的组合模式。

**建议**：维持当前继承结构（对 Godot 游戏是合理的），但更新设计文档承认"在 Sprite2D/CharacterBody2D 基础上允许深度继承，跨领域功能通过子节点组件实现"。

### 4.3 缺少统一的游戏状态管理

**问题**：设计文档规划的 `game_state.gd` Autoload 不存在。以下状态信息散落在各处：
- 当前游戏模式 → `ModeSelector`
- 地块分配关系 → `FarmlandManager._assignments`
- 工人列表 → `UnitManager.workers`
- 仓库内容 → `Storage.contents`
- 地图数据 → `TerrainGenerator`（world 节点）
- 寻路成本网格 → `PathfindingManager`

没有一个统一的入口可以查询"当前游戏世界状态"。

**建议**：实现 `GameState` Autoload，持有对其他系统的只读引用，提供统一的快照/查询接口，为后续存档系统做准备。

## 五、具体代码问题

### 5.1 UnitBase._process() 未使用 delta

```gdscript
func _process(_delta: float) -> void:
    global_position = global_position.lerp(_next_tick_position, 0.1)
```

硬编码的 `0.1` lerp 因子导致不同帧率下移动平滑度不一致。高帧率（144Hz）下物体移动过慢，低帧率（30Hz）下可能不平滑。

**建议**：使用 `_delta` 修正：`global_position = global_position.lerp(_next_tick_position, _delta * 20.0)`

### 5.2 TileActions 的 CROP_SCENES 硬编码

```gdscript
const CROP_SCENES: Dictionary = {
    "wheat_tier1": "res://scenes/crops/wheat_tire_1.tscn",
}
```

新增作物需要修改代码。注释说"后续可迁移到 JSON 配置"，但一直未迁移。

**建议**：在 `config/crops/` 下或 `item_catalog.json` 中集中管理作物 ID→场景路径映射。

### 5.3 Storage._input() 占用全局 Tab 键

```gdscript
func _input(event):
    if event is InputEventKey and event.pressed and event.keycode == KEY_TAB:
        print_contents()
```

这是调试代码，不应出现在生产系统中。如果有意保留，应：
- 移到 `DebugUI` 中
- 或在构建时通过 `OS.is_debug_build()` 条件编译

### 5.4 SelectionIndicator 的 z_index 与新的渲染排序系统冲突

`unit_base.tscn` 中 `SelectionIndicator` 的 `z_index = 5`，但新的 `ZIndexConfig` 系统使用数百到数千的 z_index 值。设计文档建议将 SelectIndicator 移到独立 CanvasLayer，但尚未实施。

### 5.5 grid_position 命名混淆

`UnitBase.grid_position` 声明的类型是 `Vector2`，存储的是**世界像素坐标**（如 `(320, 384)`），而非网格坐标。真正的网格坐标需要通过 `get_current_tile()` 获取。命名与实际含义不符。

### 5.6 多线程中的对象有效性检查不足

`TickSystem._on_tick_deferred()` 通过 `call_deferred` 从线程调度到主线程，但在等待期间发出信号的接收对象可能已被 `queue_free()`。虽然有 `_tick_connected` 的 `_exit_tree` 断连，但 `call_deferred` 的时序可能早于 `_exit_tree`。

## 十、性能考量（非紧急）

### 10.1 地块查找每 tick 多次 O(log N) 查找

`WorldUtils.find_tile()` 使用 `world.get_node_or_null("tile_X_Y")`，按名称查找节点的开销随子节点数量增长。对于 32×32=1024 节点当前可忽略，但设计文档提到最大 400×400=160000 节点时需考虑替代方案（如二维数组索引）。

### 10.2 成本网格使用 Array[Array] 存储

对于 400×400 地图，每套成本网格占用 400×400×8 = 1.28MB（float64），三套约 3.84MB。在 Godot GDScript 中数组操作开销较高，大规模地图需考虑 `PackedFloat32Array` 或 C++ 扩展。
